# ChatGPT 桌面多开技术调研与接入方案

日期：2026-09-28。结论性质：源码调研、已实现方案与验证记录。最新开发和测试状态见第 10 节。

## 1. 建议

在 PathMux 中自行实现 Rust 原生的 ChatGPT 实例管理模块，复用用户安装的官方客户端。每个实例具有固定 ID、独立桌面数据目录、独立 Codex 数据目录和经过检查的启动环境。认证交给官方客户端完成。

**用户已确认的产品方向：账号与凭证独立，工作记录支持选择性同步；优先实现可靠的跨账号接续，再考虑自动同步。** 每个实例保留自己的运行数据，由 PathMux 按用户选择复制支持迁移的记录。

技术路线有依据，但目前三个第三方项目都不足以证明“当前版本、双平台、全部数据完全隔离”。应先完成双平台验证原型，再交付正式功能。

这里需要明确两个不同目标：

- **账号与应用状态隔离，工作记录按需流转**：两个账号同时在线，分别保存登录、会话、配置、缓存；选中的工作记录可以复制到另一实例继续处理。退出或删除一个实例不影响另一个，也不删除已经复制过去的记录。这是本模块的产品目标。
- **操作系统安全隔离**：两个实例不能访问对方文件、系统凭证或本机资源。相同系统用户下的目录分离不能提供这个保证；需要独立系统用户、权限边界或虚拟机。若“彻底隔离”包括这一层，应采用每实例虚拟机，并分别验证平台支持。

不要将第一层宣传成第二层，也不要将账号云端数据与本地目录混为一谈；同一账号的云端数据仍可能按服务端规则同步。

## 3. 三个项目的实际价值

### Codex Multi Launcher

公开说明声明支持 macOS 与 Windows，为每个 Profile 分配 `CODEX_HOME` 和 `--user-data-dir`，提供账号/API 登录、历史迁移、更新等功能。README 声明 macOS 包经过签名和公证，Windows 包未签名；本次没有下载二进制验签，不能把声明当作独立验证。

关键限制：本次默认分支的公开仓库主要是产品网站、图片、文档和下载入口，未见启动器核心实现。不能审计其凭证、进程、回调和 Windows 隔离逻辑，也不应当作可直接接入的开源库。

定位：适合作为界面和功能参考，不能作为已经验证的技术底座。最新发布页面本次指向 v0.1.9。[仓库](https://github.com/JqyModi/codex-multi-launcher/tree/3a0555dfc88ba399c3adb45c47f81d49b24e2ab1) · [发布页](https://github.com/JqyModi/codex-multi-launcher/releases/tag/v0.1.9)

其使用说明中的“同步已有历史对话”是为新 Profile 创建独立副本，后续新增对话不会反向写回来源。这支持将“创建时复制”和“持续同步”区分设计，不能将产品说明理解成实时双向同步。[使用说明](https://github.com/JqyModi/codex-multi-launcher/blob/3a0555dfc88ba399c3adb45c47f81d49b24e2ab1/manual.html)

2026-09-28 复核其[历史同步说明](https://jqymodi.github.io/codex-multi-launcher/features/session-sync/)：复制范围分为项目、临时任务与全部；说明称会同时处理 JSONL、SQLite 线程记录、索引、项目路径及全局状态，并强调目标之后独立运行。这解释了为何“只复制会话文件”可能在桌面窗口中显示空白，但公开仓库仍没有足以审计其具体迁移算法的核心源码。

### chatgpt-multi-account

核心实现：独立 `CODEX_HOME`，直接运行应用包内程序，传递 `--user-data-dir`。默认不共享历史；另有显式开启的历史软链接模式，以及目录登记、备份、重置和失效锁清理。

复核[脚本](https://github.com/ccheney/chatgpt-multi-account/blob/main/codex-multi-account.sh)后确认：`--symlink-history` 共享的是同一批历史目录与状态数据库，附加选项还可共享运行数据库。这种方式无法按某条会话选择副本，也无法保持两个账号的工作记录独立演进。

优点是代码可读且有 MIT 许可。局限是仅针对 macOS、进程判断依赖命令行文本、没有完整桌面生命周期管理。历史共享会链接 SQLite 及其 WAL/SHM，项目将其标为非官方支持方案；本方案采用独立副本与受控接续，不采用多个实例直接共享可写数据库。

本机还存在明确兼容差异：脚本要求 `Contents/Resources/codex` 可执行，而本机应用使用 `Contents/Resources/codex-cli/` 布局。脚本按现状会在这个检查处失败。它也没有设置本机启动逻辑所使用的 `CODEX_ELECTRON_USER_DATA_PATH`。

定位：理解早期启动机制的参考，不宜直接包装后发布。[固定版本脚本](https://github.com/ccheney/chatgpt-multi-account/blob/6fa8815ef4cb7cc930576f761ebaabecf6891445/codex-multi-account.sh)

### ChatGPT Desktop Switcher

使用 Tauri 2 和 Rust，结构与 PathMux 接近。创建 `gui/`、`cli/` 和 `profile.json`，通过 macOS `open -n --env ... --args ...` 启动；支持运行状态、按 PID 聚焦和停止。

项目自述为个人 MVP，仅 macOS，应用路径硬编码。README 明确承认多实例登录回调需要真实账号验证。源码也未设置 `CODEX_ELECTRON_USER_DATA_PATH`。Cargo 声明 MIT；本次仓库树未见独立 LICENSE 文件，若直接复用源码，应补核许可与归属要求。

复核当前 [README](https://github.com/odiak/chatgpt-desktop-switcher) 后，该项目仍只声明创建、启动、聚焦及停止独立实例，没有会话复制或跨账号接续功能。

定位：三个项目中最适合参考模块结构；仍需自行补齐兼容、隔离验证和 Windows 实现。[源码](https://github.com/odiak/chatgpt-desktop-switcher/blob/f0f78fbffcc0d0682014b0d1bf7f3393abc39cbc/src/main.rs) · [局限说明](https://github.com/odiak/chatgpt-desktop-switcher/blob/f0f78fbffcc0d0682014b0d1bf7f3393abc39cbc/README.md)

## 4. 本机发现：双参数方案需要修正

只读检查本机包内以下文件：

- `.vite/build/bootstrap-CzzsHphT.js`
- `.vite/build/shell-env-DLtwqhYG.js`
- `.vite/build/main-C5425b_s.js`

发现以下行为：

1. 启动函数 `$E` 优先读取 `CODEX_ELECTRON_USER_DATA_PATH`，否则计算默认 `Codex` 应用数据目录。
2. 启动过程显式执行 `app.setPath('userData', ...)`。因此命令行出现 `--user-data-dir` 并不能证明最终 Electron 数据目录独立。
3. Shell 环境加载模块仅在显式桌面数据变量存在时，保存并恢复传入的 `CODEX_HOME`。启动子进程时设置成功，也不等于经过 Shell 环境导入后仍然有效。
4. 单实例锁策略也参考显式桌面数据变量。
5. 应用内部一个 Demo 启动路径同时传递下面三项。这是本机实现证据，不是面向第三方的稳定公开接口。

建议的候选启动配置：

```text
CODEX_HOME                     = <实例根目录>/codex
CODEX_ELECTRON_USER_DATA_PATH   = <实例根目录>/desktop
--user-data-dir                = <实例根目录>/desktop
```

环境变量只设置在目标子进程，不能写成全局变量。正式支持前必须验证实际文件写入位置、子进程环境和账号行为，不能只检查参数字符串。[Electron 数据路径与生命周期文档](https://www.electronjs.org/docs/latest/api/app)

## 5. 还必须覆盖的隔离漏洞

### 5.1 SQLite 的独立覆盖项

上游配置 schema 中的 `sqlite_home` 可覆盖数据库目录，默认又可能读取 `CODEX_SQLITE_HOME`。应在新实例配置中显式指定实例内数据库目录，验证相关环境变量；不能从主账号复制未经检查的配置。

PathMux 的父进程可能继承另一个开发环境的变量。应对会改变认证、数据位置和服务连接的变量建立版本化清单，清理或按实例重设；保留正常系统变量，避免破坏系统行为。也要检查官方应用后续导入 Shell 环境带来的覆盖。

[固定版本 schema](https://github.com/openai/codex/blob/18344a972ddf06aa0bb80773bfb7564576e8991b/codex-rs/core/config.schema.json)

### 5.2 账号凭证和扩展凭证不是同一套机制

上游账号认证既支持 `CODEX_HOME/auth.json`，也支持系统凭证存储。直接 keyring 后端以规范化 home 路径生成键；新代码还有 secrets-manager 后端。因此要针对安装版本验证实际后端，不能只检查是否存在 auth.json，也不能将“进程正在运行”显示为“已经登录”。

MCP OAuth 的键生成又不同：本次上游代码中普通服务器键主要按名称、URL 等生成，仅特定企业分支纳入 home。相同系统用户下不能据此承诺所有第三方连接都随 Profile 隔离。

建议首版全新实例保持独立扩展配置；需要 MCP OAuth 时，优先验证官方支持的 `mcp_oauth_credentials_store = "file"` 是否让该版本全部相关写入落在实例内。该模式涉及本地明文凭证，必须配置私有目录权限，并单独验收；它也不代表覆盖所有插件登录机制。无法验证的连接类型应标记未支持隔离。

[账号凭证源码](https://github.com/openai/codex/blob/18344a972ddf06aa0bb80773bfb7564576e8991b/codex-rs/login/src/auth/storage.rs) · [MCP OAuth 源码](https://github.com/openai/codex/blob/18344a972ddf06aa0bb80773bfb7564576e8991b/codex-rs/rmcp-client/src/oauth.rs)

### 5.3 登录回调与并行使用分开设计

上游网页登录服务首选端口 1455，存在备用端口；端口被占用时还会尝试取消旧登录服务。多个首次登录流程同时进行可能相互干扰。本机主程序另有远程连接授权流程使用 1455/1457，不能将该流程误认成所有登录的实现。

建议新实例首次授权依次进行，登录完成后并行使用。PathMux 内的授权队列只能管理自己发起的流程，不能阻止用户在客户端或 CLI 中手动发起其他登录；发现外部冲突时给出明确提示，不能主动终止未知服务。

浏览器可能仍登录着上一个账号，授权后必须核实官方客户端显示的实际账号。不要复制主账号 token。设备码流程只有在客户端与账号策略允许、并经验证后才能作为兜底。

插件回调、自定义 URL scheme、系统浏览器扩展和通知点击也需要单独测试路由，不应仅凭首次登录成功宣称全部可用。

[登录服务源码](https://github.com/openai/codex/blob/18344a972ddf06aa0bb80773bfb7564576e8991b/codex-rs/login/src/server.rs)

### 5.4 目录隔离的边界

两个 Profile 仍在同一系统用户下运行，共享文件访问权限、剪贴板、系统钥匙串服务、部分 OS 设置和可能被选择的工作目录。分别用两套项目副本可避免误写同一项目，但不能构成访问控制。

普通运行日志、崩溃报告、系统级辅助服务、下载目录和浏览器扩展配对也应列入检查清单。未确认前只能承诺已验收的状态类别。

## 6. 接入 PathMux 的设计

### 页面和用户流程

增加独立的“ChatGPT 多开”页面：显示官方应用路径、版本、兼容状态，以及每个实例的名称、运行状态、启动/打开窗口/关闭操作。创建后可在官方窗口选择 ChatGPT 账号或 API Key 登录，也可在实例卡片配置支持 Responses API 的服务地址与密钥。PathMux 从该服务的 `/models` 读取模型列表，让用户选择默认模型，并将全部返回的模型写入该实例专属的 Codex 模型目录。官方 app-server 的 `model/list` 已用合成目录验证能读取多个模型；桌面 GUI 是否显示自定义模型仍受官方登录态和客户端版本影响，没有账号登录态时可能隐藏。未提供 `/models` 的网关可手动填写模型 ID，此时目录只有该模型。API 配置只写入该实例目录，保留官方账号的 `auth.json`；切回账号登录时恢复原有模型及模型目录设置。内网 IP 或解析到内网地址的网关在模型发现时绕过系统代理，交由系统路由（包括已连接的 VPN）发送；启动官方客户端时，也只对该 API 实例设置对应地址的 `NO_PROXY`，让实际对话请求走相同路线。公网网关遵循系统网络设置，不依赖特定代理软件。私有 HTTPS 网关的 CA 证书须预先导入 PathMux，模型发现使用该 CA 验证连接，实例启动时通过 `CODEX_CA_CERTIFICATE` 交给官方客户端。名称仅为用户标签，不能冒充已验证的账号身份。

支持“关闭并保留数据”和“删除实例数据”两种明确操作。PathMux 退出不应结束用户正在使用的实例；进程管理结构需支持重启后重新识别。快捷方式和后续启动入口也要复用同一启动配置与兼容检查。

增加“从已有实例复制记录”和“发送到另一账号继续”入口，展示来源、目标、包含的对话与附件，以及无法迁移的内容。具体流程见下方“工作记录同步与跨账号接续”。

建议目录：

```text
<PathMux 本地应用数据>/chatgpt/
  registry.json
  transfers/<迁移 ID>/
    manifest.json
    staging/
  profiles/<不可变 ID>/
    profile.json
    desktop/
    codex/
      config.toml
      db/
    logs/
```

名称可以改，ID 与凭证对应路径保持稳定。macOS 使用系统 Application Support 位置；Windows 使用 LocalAppData 下的本地位置，避免浏览器状态跟随漫游配置同步。

`transfers/` 保存迁移清单和临时快照，不作为官方客户端共用的数据目录。临时内容按明确的完成、失败与保留策略清理，清单不记录登录凭证。

### 工作记录同步与跨账号接续（用户已确认）

#### 目标与边界

用户观察到：当前 ChatGPT 桌面端退出登录，再登录另一个账号后，工作记录仍然保留。这个现象与“保留本地工作数据，只更换认证身份”的机制一致，但尚未在本次调研中复现，不能据此推断所有云端聊天、附件和工具授权都可跨账号迁移，也不能证明多个实例可以安全并发写同一份历史。

本功能优先处理经过验证的本地工作记录。账号 token、Cookie、系统凭证、插件/MCP 授权、运行锁和进程状态保持各自独立。记录正文与附件可能包含敏感内容，用户选择同步即代表这些内容将复制到目标实例，并可能在续聊时由目标账号发送处理；操作页应清楚展示目标和范围。

| 模式 | 行为 | 实施决策 |
| --- | --- | --- |
| 创建时复制历史 | 将选定历史复制到新实例，之后各自新增 | 纳入支持范围，先验证数据格式 |
| 按需同步与接续 | 将选定任务及支持迁移的上下文、附件复制到另一实例继续处理 | 优先实现 |
| 后台持续同步 | 两个账号窗口同时运行，所选项目的新会话和轮次自动出现在另一窗口 | 用户已明确要求；当前未实现，技术阻塞见第 11 节 |
| 实时共用全部历史 | 多实例直接读写同一份数据库和会话文件 | 不作为本方案的实现方式 |

#### 用户流程

1. 账号 A 完成一段工作后，选择任务和“发送到账号 B 继续”。实例名称是标签；实际登录身份可验证时应同时展示，否则明确标注未核实。
2. PathMux 列出可迁移的对话、上下文、附件，以及缺失文件、云端引用或需要重新授权的工具。
3. 在任务停止写入的安全时点取得一致快照；如当前版本无法可靠地在线导入，明确要求关闭相关实例后操作。
4. 在 B 中创建独立副本，记录来源实例、来源会话、快照版本与目标会话的对应关系。优先使用客户端支持的导入/分叉能力；没有可用接口时，文件适配必须按版本验证。
5. 在官方客户端验证记录可打开，并验证续聊。B 的后续记录属于 B 的分支；A 的原始记录保留。

#### 同步和冲突规则

- 仅复制已选择并列入白名单的数据；不整包复制 `CODEX_HOME` 或桌面数据目录，不复制账号与工具凭证。
- 不能简单复制正在写入的 SQLite 文件及 WAL/SHM；使用经过验证的一致快照机制，或在相关实例完全退出后处理。目标导入同样需要避免与客户端并发写入。
- 同一份快照重复导入应去重。来源和目标都有新增内容时保留两个分支，不按更新时间覆盖，不自动拼接成一条对话。
- 数据和附件先写入临时位置并校验，成功后提交迁移结果；失败可回滚，不能留下半条会话或损坏目标索引。
- 删除来源实例或来源对话，不级联删除已导入的副本。删除操作不跨实例传播。
- 引用本地文件不等于已迁移文件；接续前验证附件、项目目录和工作树引用。项目文件的复制或共享单独列明，避免两个实例无意修改同一份工作文件。
- 云端会话 ID、受账号控制的附件和授权不能仅靠文件复制变成目标账号可用。无法迁移的内容明确标记；仅能导出文本时标为“历史导出”，不能显示“接续成功”。

#### 完成标准

只有目标官方客户端能正确打开导入记录、读取声明支持的上下文与附件，并用目标账号继续对话，才能标记“可接续”。在列表中显示标题或能浏览文本只能证明部分导入。源账号退出、源实例删除后，已经声明为独立副本的目标内容仍应可用。

### 后端模块建议

```text
src-tauri/src/chatgpt/
  mod.rs             Tauri 命令与类型
  discovery.rs       安装发现、产品识别、版本与兼容能力
  profiles.rs        实例注册、目录、权限、原子写入
  launch.rs          启动计划、子进程环境、路径检查
  process.rs         运行状态、聚焦、关闭与恢复识别
  history.rs         可迁移记录发现、范围预览与版本适配
  transfer.rs        一致快照、导入、去重、分支与回滚
  diagnostics.rs     隔离验证与脱敏诊断
  platform/macos.rs
  platform/windows.rs
```

前端入口接入 `src/App.tsx`，类型和调用接入 `src/api.ts`。现有 `workbuddy.rs` 的安装发现和平台提示可参考设计，但其网关配置逻辑不属于这里。

现有 MCP 同步有全局 Codex 目标。新增实例应成为明确独立目标，禁止启动时自动将全局 MCP、Skills、Plugins 或凭证同步到所有实例。首版先保持各实例独立，后续按用户选择增加单实例同步。

### macOS

- 检测系统和用户 Applications 目录，并支持手动选择。
- 读取 Info.plist 和包内能力标记，不能只认名称或旧的 CLI 路径。
- 使用系统新实例启动机制传递三项配置；需要同时取得或可靠关联实际主进程。
- 按 PID 聚焦与关闭，操作前检查进程身份、启动时间及实例归属。
- 复用官方应用包，保持原有签名；不修改 bundle ID、不重签名、不注入补丁。
- 主客户端和独立实例共用应用包标识。主客户端退出后，Spotlight 或应用图标可能只激活仍在运行的实例；页面提供「打开主 ChatGPT」，识别已有主进程后聚焦，否则用系统 `open -n` 新开默认数据目录的主进程，不关闭实例。此行为仍需在 macOS 界面中验收。

### Windows

- 分别处理普通安装与 Microsoft Store/MSIX 安装，支持自动发现和手动兜底。
- 可用包元数据取得安装位置；这只是发现手段，不等于证明可正确启动。不能硬编码 WindowsApps 版本路径。
- 根据安装类型验证原生启动方式、包身份和子进程环境传递。若直接运行 exe 会失去所需包身份，应使用对应系统启动机制并重新验收。
- 记录进程身份和开始时间，避免 PID 重用时关闭其他程序；优雅关闭后才考虑针对本实例的强制终止。
- 更新后重新发现应用位置，保持 Profile 数据路径稳定。

[微软包信息查询文档](https://learn.microsoft.com/en-us/intune/configmgr/protect/deploy-use/find-a-pfn-for-per-app-vpn)

### 防止误删与串用

- 所有路径由后端按 ID 生成，不接受前端提供任意数据根目录。
- 检查路径规范化、大小写、软链接和 Windows junction/reparse point；不同 Profile 不能指向相同实际目录。
- 创建、启动与删除加实例锁，元数据原子写入。
- 删除只能作用于有登记和所有权标记的托管目录；运行中拒绝删除，不清理默认账号。
- 不因发现 SingletonLock 就直接删除；先确认没有占用该目录的活进程。
- 删除凭证必须针对对应实例的已知后端；不能只删目录后就宣称系统凭证也已清除。

## 7. 为什么选择这条路线

| 方案 | 适配本需求 | 判断 |
| --- | --- | --- |
| PathMux 原生管理官方客户端独立 Profile | 保留官方功能，贴合现有 Rust/Tauri，能控制版本与生命周期 | 推荐，需双平台验证 |
| 直接调用第三方启动器 | 引入外部安装和版本依赖，核心实现未必可审计 | 不作为产品底座 |
| 直接包装现有 Shell 脚本 | 当前本机布局和启动参数已有兼容缺口，Windows 仍需重做 | 仅作技术参考 |
| 复制应用、改 bundle ID、重新签名 | 更新、系统授权和回调维护成本高 | 不选为主方案 |
| WebView 或浏览器独立 Profile | 可做网页账号隔离，但无法保证官方桌面完整能力 | 可作为另一个产品功能 |
| 每实例独立系统用户或虚拟机 | 能建立更强权限边界，资源与体验成本更高 | 适合要求 OS 级隔离的场景 |

## 8. 实施顺序与验收门槛

### 第一阶段：验证决定可行性的行为

在 macOS 和 Windows 的受支持安装类型上创建两个全新临时 Profile，按候选参数启动，验证实际数据落点和运行时环境。之后用两个真实账号依次完成首次授权，并行重启使用。

同时验证一条本地任务从 A 复制到 B 后的实际续聊，覆盖上下文、附件、项目路径和账号身份；单独记录云端任务等不支持的类型。验证通过前不承诺完整跨账号接续。

先完成此阶段，再扩展完整管理界面。源码证据不足以替代真实账号、包身份、回调和升级验证。

### 第二阶段：集成管理功能

完成应用发现、兼容检查、实例创建、启动、聚焦、关闭、保留数据、删除、脱敏诊断。状态应区分“运行中”“登录状态未知”“待验证版本”，避免误导。

集成创建时复制历史与手动跨账号接续，完成范围预览、版本检查、快照、目标导入、来源映射、去重及失败回滚。按用户补充需求，增加在切换账号时选择单条、整个项目或全部本地会话并同步；来源窗口可以保持打开，复制只取已经完成的回复。

### 第三阶段：回归与发布

| 场景 | 必须通过的结果 |
| --- | --- |
| A/B 账号与默认实例共存 | 各自显示正确账号，窗口不被错误复用 |
| 冷启动、重启机器、重启 PathMux | 登录和会话留在各自实例，运行状态可恢复 |
| 新聊天、附件、配置与数据库 | 写入本实例路径；以受控数据做差分核验 |
| A 退出登录 | B 仍可使用，B 的凭证和会话不变 |
| 创建 B 时复制 A 的选定历史 | 仅选定记录和支持的附件进入 B，凭证与工具授权不随之复制 |
| A 的任务发送到 B 继续 | B 用自己的账号续聊，上下文与附件符合声明范围，A 的记录保留 |
| 同一快照重复导入 | 正确去重，目标已有进展不被覆盖 |
| A/B 对同一来源任务分别续聊 | 保留两个分支和来源关系，不自动合并或覆盖 |
| 同步期间有写入或导入中断 | 延后到安全时点或使用已验证的快照；失败回滚，双方记录完整 |
| 云端引用、缺失附件、失效项目路径 | 明确提示可迁移范围，不误报完整接续成功 |
| 来源实例删除 | 已导入目标的独立副本继续可用，不传播删除 |
| 同时发起首次登录 | 有明确队列或冲突提示，不静默取消另一实例授权 |
| 插件、MCP、浏览器与远程连接 | 按声明支持范围逐项验证凭证与回调归属 |
| 父进程已有 Codex/API/SQLite 变量 | 不继承成其他实例的数据或认证来源 |
| 中文与空格路径、同名点击启动 | 路径正确，ID 不变，一个 Profile 不发生并发写入 |
| 崩溃与残留锁 | 恢复只影响目标实例，活进程锁不被误删 |
| 更新客户端 | 检查版本和能力，数据路径保持稳定；不支持时明确阻断 |
| 删除 A | B 和默认实例保持完整；列明本地凭证清理范围 |
| PathMux 退出 | 已启动官方实例继续运行 |

自动化覆盖两个平台的纯逻辑和生命周期规则，CI 同时跑 Windows/macOS；真实设备验证登录、窗口、回调与更新。遵循项目现有发布检查，不能把单平台编译成功写成跨平台完成。

- 界面明确显示「验证阶段」，不推断登录账号，也不显示未经核实的「已登录」状态。

## 11. 新增需求：两个窗口同时运行时持续同步项目

用户进一步明确：选择一个项目后，A/B 两个官方窗口同时运行；此项目后续产生的对话应自动出现在另一账号，并能在原会话中继续。这一要求**尚未实现，也不能用现有一次性复制冒充**。

当前官方客户端的本地会话协议支持读取、恢复与分叉；[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)说明 `thread/inject_items` 只向模型可见历史追加原始 Responses 项目，不启动用户轮次。我们已实测旧版 `thread/fork` 会丢失新版分页会话的展示事件，因此不能把“模型记得历史”当作“两个窗口实时显示同一条会话”。在目标窗口保持运行时直接替换 JSONL 或共享可写 SQLite 会与客户端进程的索引、缓存及并发写入冲突；[chatgpt-multi-account 的共享模式](https://github.com/ccheney/chatgpt-multi-account/blob/main/codex-multi-account.sh)也将历史软链接标为不受支持，并要求改变共享链接前先退出窗口。[Codex Multi Launcher 的说明](https://jqymodi.github.io/codex-multi-launcher/features/session-sync/)只保证创建独立副本，后续内容不会写回来源。

2026-09-28 在 Mac 的官方 ChatGPT `26.924.22138` 内置会话服务上又做了隔离实验：创建两个无登录凭证、不同 `CODEX_HOME` 和 SQLite 目录的临时实例，各自启动一条新会话。对 B 调用 `thread/inject_items` 注入合成的用户提问与助手回答，调用返回成功；随后 B 的 `thread/read(includeTurns=true)` 返回 0 个可见轮次，`thread/items/list` 返回 0 项，两者均不包含测试标记。实验程序结束后关闭两个服务并删除临时目录。这直接排除了用该接口实现窗口可见问答实时镜像的方案；它没有操作真实 A/B 账号或证明其他未公开接口不可用。

因此目前可验证的行为是：用户主动同步项目时，复制当时已完成的全部本地会话；之后的新轮次在下次主动同步时生成新的独立快照，不覆盖另一账号已经继续的分支。若要达到双窗口后台实时、同一条可见会话双向同步，需要官方提供面向运行中会话的可见轮次导入及变更通知接口，并定义两个账号同时修改同一会话时的冲突合并规则。获得可验证的接口前，不启用共享可写数据库或运行中改写会话文件。

双窗口后台实时同步的验收结果仍为**未实现、未通过**。用户随后明确要求发布正式新版本，因此本次只发布已实现的隔离多开和按次复制，发布说明必须清楚列出该缺口；不用按次复制的通过结果替代实时同步验收。
