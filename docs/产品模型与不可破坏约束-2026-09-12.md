> **来源**：用户 2026-09-12 给出的产品模型，经逐条对着代码核实（下方「已核实的偏差」每条都带 `file:line`）。

## 一、产品定位（一句话）

> **本产品的核心不是"切换 Claude 配置"，而是让同一个项目中的多个终端，以互不干扰的方式同时连接不同网关。**

```
项目目录
├─ 终端 A：claude            → 官方 Claude，保持原样
├─ 终端 B：claude corp       → 公司网关
├─ 终端 C：claude test       → 测试网关
└─ 终端 D：claude partner    → 合作方网关
```

这些终端**同时运行**。**关闭管理中心不影响已生成的命令与后续启动。**

### 用户不应感知"当前环境"

没有全局的"当前选中环境"这种运行状态。**每次启动命令独立决定用哪个环境。**

## 二、对象模型

| 对象 | 定位 | 应用权限 |
|---|---|---|
| **默认 Claude** | 用户直接 `claude` 启动的官方环境 | **只读统计**，不修改配置 |
| **网关环境** | 网关地址 / Key / 模型映射 / 独立会话目录形成的启动预设 | 应用负责配置与删除 |
| **独立登录环境** | 独立的 Claude 配置目录；登录由 Claude Code 官方流程完成 | 只创建隔离目录，**不接管登录凭据** |
| **全局共享资源** | Skills / Agents 的共享文件，以及 MCP / 插件的共享管理策略 | **应单独定义**，不得混同于默认 Claude；Skill 同时面向 Claude 环境与 Codex；Agents 面向 Claude 环境；插件文件和安装账本归各环境独立持有；Commands 只做存量兼容迁移 |
| **默认 Claude** | **不是一种可配置环境，也不是同步中心。** 只是统计中的一个来源，表示"直接运行官方 `claude` 产生的数据" | 仅统计 |

## 三、与 cc-switch 的区别（只写我们能自证的）

> **不得**宣传成"另一个软件必须一直开着" —— 那取决于对方实现，不是可靠结论。以下各条均由本仓库代码可自证：

- 没有全局"当前环境"。
- 不改写全局网关配置来完成切换。
- 网关参数**只作用于当前一次 Claude 进程**。
- 同一项目可以**并发**连接多个网关。
- 一个终端退出或更换环境，**不影响**其他终端。
- 桌面管理中心是**配置工具**，不是运行中的代理服务。

### 界面措辞要求

**不要**用「切换到环境」「跑完自动恢复」。应说：

> 仅本次命令使用该环境，其他终端和默认 Claude 不受影响。

## 五、不可破坏的产品约束

1. `claude` 必须**无条件透传官方 CLI**：零写入、零同步、零环境变量污染。
   **透传的范围要写准（2026-09-12 收窄）**：承诺的是**参数与原生退出码**透传。
   PowerShell 的函数包装器**无法**让调用方的 `$?` 反映原生进程的失败（本机实测：
   能改变 `$?` 的只有 `$PSCmdlet.WriteError`，而它要求 advanced function，会破坏参数透传），
   所以 PowerShell 下请用 `$LASTEXITCODE` 判断结果 —— 该值由脚本**显式回写**，
   成功为 0、失败保留原始非零值。**不得承诺"PowerShell 状态语义完全一致"。**
2. `claude <环境名>` **只影响本次子进程**。
3. **不保存**"当前选中环境"这种全局运行状态。
4. 默认 Claude不参与配置修复与双向同步。除洞察统计外，只有用户主动使用或启用「从默认 Claude 导入」时，应用才把它作为**只读发现来源**；任何路径都不得写回。
5. 网关环境的 **Key、地址、CA、模型映射彼此隔离**。
6. 独立登录环境**只隔离目录**，认证完全交给 Claude Code。
7. **管理中心关闭后，已配置环境仍能启动**。
8. **同一项目、多个终端、多个网关**必须作为主要测试场景。
9. 环境名应**避开 Claude 官方子命令**（如 `mcp`、`doctor`、`update`），防止 `claude mcp ...` 被误认为环境。
10. 后续增加统一的 **`ccm <环境名>` 启动器**：解决 cmd.exe，并让 PowerShell / bash 包装函数最终都调用同一套启动逻辑。

## 六、整改优先级

先保证默认 `claude` 完全无副作用，再依次拆除默认 Claude双向同步与模型修复，随后处理 CA 注入、共享资源归属、统计扫描范围。

> **第 9 条建议提前**：它不是架构问题、是**现成的坑** —— `generate_sh` 的 `case "$1"` 直接拿第一个参数匹配环境名，
> 若有人把环境命名为 `mcp`，则 `claude mcp add ...` 会被当成切环境。`valid_name` 目前只挡字符集、
> `__` 前缀与 Windows 保留名，**未挡 Claude 子命令**。

## 七、已确认的决策（2026-09-12 用户裁定）

> 上一版此处为「待确认」的 4 点，现已全部裁定。**以下为实现依据，不得自行偏离。**

### 7.1 `ccm` 启动器 —— 留到重构后再说

本轮**不做** `ccm`。先把五件事做完：默认 `claude` 零副作用、拆双向同步、CA 注入、共享资源归属、统计口径。
`ccm` 单独立项。**B#7 的 cmd.exe 结论因此暂不变更**（仍为「未支持」）。

### 7.2 共享 MCP —— 应用自建共享源，**单向分发**

共享 MCP 归应用管理：

```text
~/.cc-manager/shared/mcp.json
                 ├─ 单向分发 → 环境 corp
                 ├─ 单向分发 → 环境 test
                 └─ 单向分发 → 环境 partner
```

**默认 Claude 的 `~/.claude.json` 完全不参与。**

界面需明确**三种作用范围**：

| 作用范围 | 语义 |
|---|---|
| **所有环境** | 由应用统一维护并**单向分发** |
| **指定环境** | 只写入所选环境 |
| **当前项目** | 使用项目自身的 MCP 配置，**不进入**全局共享库 |

- **删掉**现有这句：「MCP 与插件启用状态在每次启动 Claude 时双向同步。」
- **替换为**：「应用管理的共享配置会自动分发到所有环境；各环境自己的配置保持独立。」
- 实现上**必须坚持单向分发**，避免再次形成复杂的多副本双向合并。
- 环境里出现**同名 MCP** 时，**环境配置优先**，但**必须显示冲突提示**。

### 7.3 共享资源迁移 —— 复制 + 原子切换环境链接

**不移动、不删除、不链接默认 Claude；复制后只切换受管理环境。**

> 上一版设想的「移动内容」是错的：那会删掉 `~/.claude/` 里的东西；即便随后给默认 Claude 建链接，
> 也等于继续干预默认 Claude，违反"只读"约束。

步骤：

1. **复制**（不是移动）Skills / Agents 到应用共享目录：
   `~/.claude/{skills,agents}` → `~/.cc-manager/shared/{skills,agents}`。
   插件不属于文件共享范围，见 7.5。
2. `~/.claude/` 原内容**保持不动**，默认 Claude 继续用自己的资源。
3. 把所有**受管理环境**的 Skills / Agents 链接改指向 `~/.cc-manager/shared/`。
4. 迁移后两边正式独立：默认 Claude 用 `~/.claude/`，受管理环境共享 `~/.cc-manager/shared/`，**后续不再自动互相同步**。
5. **同名处理**：
   - 内容相同 → 直接去重
   - 同名但内容不同 → **不覆盖**，保留原文件并**报告冲突**
6. **必须可回滚**：
   - 先复制到临时目录并**校验文件数量与内容**
   - 记录每个环境**原来的链接目标**
   - 全部复制成功后才切换链接
   - 任一环境重建链接失败 → **立即恢复所有旧链接**
   - 成功后记录**迁移版本**，避免重复执行

> 迁移后虽然有两份内容，但含义不同：一份属于默认 Claude，一份属于受管理环境。
> 这不是"两套共享根"，因为默认 Claude 那份**不再参与环境共享**。

界面提示：

> 已将现有扩展复制到应用共享库。默认 Claude 的原有文件保持不变；受管理环境今后使用独立的共享资源。

### 7.4 默认 Claude模型钉死 —— 保留只读告警，删除一键修复

**「只读」不等于不能检查。** 应用可以发现风险并说明原因，但**不能替用户改写**默认 Claude 的配置。

提示文案：

> 检测到默认 Claude 配置固定使用模型 `{model}`。当你从用户主目录启动网关环境时，
> 该设置可能覆盖环境的模型映射。应用不会修改此配置。建议从实际项目目录启动；
> 如需调整，请在 Claude Code 中自行修改。

处理规则：

- 只**读取并识别** `model` 字段
- **不显示**「一键恢复」按钮
- **不自动删除或改写**字段
- **只在存在网关环境时**提示
- 明确说明主要影响「**从用户主目录启动**」的场景
- **诊断详情中可展示文件路径**，方便用户自行处理

### 7.5 插件管理 —— 各环境独立安装，应用共享策略（2026-09-13 用户确认）

1. `.claude/plugins`、插件缓存和 `installed_plugins.json` 归每个环境独立持有，不做目录链接或文件复制；
2. 应用共享库只保存插件身份（`plugin@marketplace`）、版本策略和环境的继承 / 启用 / 停用 / 排除策略；
3. 安装、启用、停用、更新、卸载都由应用为目标环境设置 `CLAUDE_CONFIG_DIR` 后调用 Claude Code 官方 CLI；
4. 默认 Claude 仅用于只读发现已安装插件，用户选择后是在其他环境**重新独立安装**，不是复制默认 Claude 的文件；
5. 「所有环境」是逐环境执行并逐项报告结果，不建立共享插件目录，也不要求跨环境事务回滚；
6. 调用插件命令不得携带网关地址、模型 Key 或网关 CA；
7. 当前已经存在的共享插件目录必须通过可回滚迁移逐环境退出。迁移失败的环境保持旧链接并标记待迁移，全部环境完成前不删除旧共享目录。
8. 安装、启用或停用后，新启动的 Claude Code 会话直接生效；已经运行的会话需要分别执行
   `/reload-plugins`，无需关闭终端窗口。包含 monitors 的插件需要重启 Claude Code 会话；
9. 应用只提示待重新加载，不得强制中断或向正在工作的 Claude Code 会话注入命令。

### 7.6 Skill 管理规则（2026-09-13）

> 「共享 Skill 默认立即在所有环境生效」以及「环境同名版本优先、不弹冲突决策、显式恢复继承」
> 已经用户确认。其余条目属于保证数据安全和跨平台一致性的实现约束，由技术方案收敛，不再要求用户选择。

1. 共享库以一个完整顶层 Skill 为管理和事务单位，禁止对同名 Skill 逐文件混合；
2. 环境不链接整个 `skills` 目录，改为按 Skill 单独链接，以支持继承共享 / 环境覆盖 / 环境排除 / 环境独有；
3. **共享 Skill 新增或更新成功后，默认立即在所有环境生效**（已确认）；
4. 环境同名本地版本优先并标为环境覆盖，不弹冲突决策，共享版本不得覆盖（已确认）；
5. 只有用户主动执行「恢复继承」，环境才重新使用共享版本（已确认）；
6. 从默认 Claude 导入符号链接 Skill 时复制经校验的独立快照，不把外部链接传播到所有环境；
7. 删除共享 Skill 时清理继承链接但保留环境独有/覆盖版本，并记录忽略项，防止机会式自动导入重新复活；
8. 当前整目录链接必须通过逐环境、可回滚迁移改为逐 Skill 链接。
9. Claude Code 2.1.0 起对正常路径中的独立 Skill 支持热加载；逐 Skill Junction / 符号链接是否同样稳定，
   必须通过 Windows 与 macOS 真机验证。产品不得用 `/reload-plugins` 掩盖独立 Skill 热加载缺陷；
10. 共享 Skill 变更后应刷新受影响环境的目录项以触发监听。若链接方式无法稳定热加载，必须调整分发机制。

### 7.7 Commands 退役 —— 只保留存量兼容迁移（2026-09-13 用户确认）

1. PathMux 不提供独立 Commands 页面，不新增 Command 创建、安装、共享或自动导入能力；
2. Claude Code 内置命令不属于 PathMux 管理范围；
3. 用户已有 `.claude/commands` 文件不得在升级时直接删除；
4. 存量自定义 Commands 后续通过一次性迁移转换为 Skills，转换和验证成功后才退出旧链接；
5. 同名 Skill 已存在时不覆盖，原 Command 保留到迁移备份并报告待处理；
6. 当前代码中的 `commands` 共享目录和扩展卡片属于待退役实现，不得继续作为新功能基础。

### 7.8 Codex Skill 与共享 Agents 的目标范围（2026-09-13 用户确认）

1. 共享 Skill 默认立即应用到所有 Claude 环境和 Codex/ChatGPT 桌面工具；
2. 默认 Claude 仍是只读发现来源，不因为 Codex 接入而成为写入目标；
3. Codex 的系统 Skill 目录不得修改或遮蔽，既有 `~/.agents/skills` 与 `~/.codex/skills` 内容不得静默覆盖；
4. Claude 与 Codex 共同支持 Agent Skills 的核心结构，供应商专属字段必须检测兼容性，不得擅自重写；
5. 共享 Agents 默认应用到所有 Claude 环境；Claude 自定义子代理与 Codex 的线程/Agent 不是同一种配置，不做自动转换；
6. Agents 默认分发到所有 Claude 环境；采用原子复制与分发记录，允许环境覆盖 / 排除 / 环境独有；
7. Agent 缺少 Skill 或 MCP 依赖时标记不可用，不自动恢复 Skill、不自动安装或开启 MCP；
8. 删除共享 Agent 只清理仍在使用共享版本的副本，保留环境覆盖与环境独有版本；
9. 上述 Agents 分发规则已经用户确认；运行中会话能否即时发现 Agent 变更仍须双平台验证。

### 7.9 功能旁的工作原理说明（2026-09-13 用户确认）

1. Skills / Plugins / Agents / MCP 及作用范围、覆盖、排除、自动导入等关键功能旁提供圆形 `?` 按钮；
2. 悬停显示一句提示，点击从右侧打开「它是怎么工作的」面板；
3. 面板顶部按「能做什么 / 点击后发生什么 / 影响哪些地方 / 还要做什么」提供简明使用说明，并包含一个真实例子；
4. 面向程序员的「设计原理」是面板主要内容，默认展开，至少说明数据源与目标、更新与覆盖判断、失败保护、运行时生效方式和主要代码入口；
5. 可以使用准确的实现术语，但首次出现必须附带白话解释；流程优先用小图、路径示例或伪代码表达，不堆放大段源码；
6. 说明内容必须与真实行为和版本限制同步，不能用文案掩盖未实现或未验证的热加载、迁移和失败处理；
7. 主要代码入口只列稳定的模块或文件，不固化容易失效的行号；需要继续深挖时再展开更详细的诊断信息；
8. 说明内容跟随懒加载页面加载，不得扩大首页初始包；
9. 按钮和侧栏必须支持键盘、屏幕阅读器和焦点恢复。
