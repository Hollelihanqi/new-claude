# ChatGPT 首条消息后权限入口消失排查

日期：2026-11-12，北京时间。范围：用户提供的主 ChatGPT 两张截图；当前对话运行在 PathMux 打开的独立实例。

## 结论

本次直接原因指向官方客户端中新建页与 ChatGPT Work 会话页的权限入口渲染差异：新建页注入 `homeLeadingControl`，其中包含 `PermissionsModeDropdown`；进入会话页后，首页控件不再渲染。已有 ChatGPT 会话的输入框没有同等的常规权限入口，另一个入口依赖额外的 `workSetup`，不能把首页上出现的按钮视为会话页也一定具有该按钮。

这解释了“发送前有，发送后没有”的时点。现有证据不支持“新实例把主程序的权限显示设置关闭”这一判断，也不能把按钮消失等同于实际执行权限被撤销。是否为上游有意限制或尚未补齐的界面行为，不能仅凭本机代码确认。

本次还发现该会话初始化请求两次返回 `conversation_inaccessible`，随后会话重新读取成功。这是实际请求异常，但没有证据证明它导致权限入口隐藏，也不能仅凭此错误认定账号串用。

## 官方客户端代码链路

只读解析安装包 `app/resources/app.asar`，没有执行提取出的客户端代码，也没有改写官方安装资源。下面的位置为归档内部路径及 JavaScript 字符串的 UTF-16 起始索引，均在对应文件第 1 行。

1. `webview/assets/async/244404.f80163303b.js`，索引 `157963`：新建页向 ChatGPT 输入框传入 `homeLeadingControl`，值可以是 `PermissionsModeDropdown`，`conversationId:null`。部分参数还根据实际运行位置决定，首页显示本身不能证明已创建会话的权限契约。

3. 同一文件索引 `312526`：另一入口的条件为 `ly && !sC && null != rt`，其中 `ly` 来自功能 gate `2163293173`、`sC` 是图片标注状态、`rt` 是传入的 `workSetup`。没有 `workSetup` 时，该分支不产生权限控件。

## PathMux 影响链核对

- `chatgpt::mod::chatgpt_open_primary` → `process::open_primary` → 商店应用正式激活入口。此路径不调用独立实例的运行框架设置同步。
- 独立实例普通启动、打开目标会话均进入 `process::launch_at`。运行中实例走 `reopen`；停止后的启动才依次准备共享沙箱凭证、实例运行框架和独立环境。
- `launcher::prepare_runtime` / `sync_runtime_preferences` 读取默认 home 的运行框架设置，写入目标为独立实例的状态文件；不向主程序写入权限显示偏好。
- `process::configure` 明确设置独立的 `CODEX_HOME`、`CODEX_ELECTRON_USER_DATA_PATH`、`CODEX_SQLITE_HOME`，包内助手在启动客户端前恢复这些环境值。
- `sandbox::prepare_profile` 确实可能同步默认 home 与各实例的机器共享沙箱凭证及初始化 marker；所以不能笼统宣称多开完全没有任何共享资源。该机制不写账号登录凭证、权限菜单显示偏好或批准策略。本次没有证据把它与菜单消失建立因果关系。
