## 一、总体结论

这是一个**工程纪律明显高于平均水平**的桌面应用：

- MCP 的 preview/apply/revision/事务回滚、CA 按网关隔离、扩展的三方比对、凭据脱敏、插件包 SSRF 防护、更新清单签名校验，设计都很认真，注释也解释了“为什么”。
- 但代码规模已经进入“单文件数千行 + 多套并行持久化实现”的阶段，**架构债开始显性化**：主线程重 I/O、启动期全量副作用、重复读取/重复哈希、多文件部分提交、前后端手工镜像契约。
- 当前最需要优先处理的不是“功能缺失”，而是 **凭据边界、环境名注入、探测副作用、主线程阻塞** 四类问题。

## 三、P0：必须优先修复

### P0-1 MCP 凭据通过 IPC 与界面明文暴露

**证据链**：

- 后端把完整配置直接放进 `McpService`：
  - `mcp/storage.rs:3156`、`3195`、`3264`、`3313`：`config: config.clone()`。
  - `api.ts:224-237` 的 `McpService.config: Record<string, unknown>`。
- 共享覆盖记录同样保存原始值：
  - `mcp/storage.rs:3410-3417`：`shared_value: info.shared_value`、`env_value: info.env_value`。
  - `api.ts:356-365` 的 `McpSharedOverride`。
- 前端**直接把原始值打印出来**：
  - `McpPanel.tsx:627`：`共享值为 <Code>{JSON.stringify(o.sharedValue)}</Code>`
  - `McpPanel.tsx:632`：`该环境当前是 <Code>{JSON.stringify(o.envValue)}</Code>`

**影响**：

1. 只要 MCP 的 `env`/`headers` 里有 token、Authorization、API Key，打开 MCP 页就可能**在屏幕上明文显示**（共享覆盖告警）。
2. 完整配置已经进入 WebView 的 JS 堆。React 转义只防 XSS 注入，不防“已经存在于 renderer 的敏感值”被读取/导出/截图。
3. 这与代码注释中“界面把敏感值脱敏后展示、保存时保留完整配置”的边界不一致：脱敏只发生在详情预览和抽屉里，列表/共享覆盖没有。

**建议**：

- 在 Rust 边界就把 `config` 和 `sharedValue/envValue` 脱敏，前端只接收 `sensitivePaths` + 占位符。
- MCP 编辑抽屉不要依赖“前端持有完整旧值”，改为后端 merge：前端提交 REDACTED/未修改标记，后端用磁盘上的原值回填。
- 共享覆盖告警只显示“哪些字段不同/已隐藏”，不显示原值。
- 增加回归测试：`serialize(McpState)` 的输出中不得出现已知 secret 字符串。

### P0-2 环境名校验不足：可破坏全部终端集成，也可劫持官方 CLI 参数

**已复现**：

1. 名称 `esac` 被 `valid_name` 接受（`main.rs:921-937`），`can_have_terminal_entry` 也接受（`main.rs:990-992`），于是 `generate_sh` 写出：
   ```
       esac)
   ```
   （`main.rs:614-622`）。本机执行 `bash -n` 得到：
   ```
   syntax error near unexpected token `)'
   ```
   结果是**整个 `cc.sh` 无法被 source**，所有环境的 `claude <名字>` 入口一起失效；`install_integration` 仍然返回成功（它不检查脚本语法）。
2. 名称以 `-` 开头同样被接受。前端正则 `^[A-Za-z0-9_-]{1,40}$`（`ConfigPanel.tsx:205`）和后端 `valid_name` 都允许。生成了 `case` 分支 `-p)` 后，本机验证 `f -p` 会进入该分支：
   ```
   HIJACKED
   ```
   即用户创建名为 `-p` 的环境后，`claude -p "..."` 会被当成“切换到 -p 环境”，官方 CLI 的 `-p`、`--help`、`--version`、`--dangerously-skip-permissions` 等参数全部被劫持。
3. `can_have_terminal_entry` 只检查 `script_safe_name` 与官方子命令冲突，没有检查 `.`、`..`、`__` 前缀（`main.rs:969-992`）。`generate_sh/ps1` 直接遍历 `list`，不经过 `profile_names` 的过滤（`main.rs:615,742`）。
   - 若 `config.json` 被手工改成包含 `..`，生成的 `_cch="$HOME/.claude-split/../.claude"` 会指向**默认 Claude** 的配置目录，造成环境串用。
   - `__main__` 也会被写入终端入口，而用量统计把它当成默认 Claude 的保留键。

**建议**：

- 在 `valid_name` 和 `can_have_terminal_entry` 同时拒绝：以 `-` 开头、`.`、`..`、`__` 前缀、所有 bash 保留字（至少 `esac`，建议完整 reserved word 列表）。
- 生成脚本后做一次真实 `bash -n` / PowerShell 解析校验；失败则拒绝写入并报错。
- 增加回归测试：名称 `esac`、`-p`、`--help`、`..`、`__main__` 不得生成入口；`generated_sh` 必须能被 `bash -n` 解析。

### P0-3 预热页面触发 MCP 探测：创建目录并启动外部进程

**证据链**：

- `App.tsx:486` 在启动后 1100ms 预热 `McpPanel`（`PersistentPage` 在 inactive 时也会挂载，见 `PersistentPage.tsx:31-35`）。
- `McpPanel.tsx:280-282` 的 mount effect 无条件执行：
  ```ts
  void Promise.all([load(), probeConnections(), loadUpdateInfo()]);
  ```
- 后端 `probe_mcp_connections`（`mcp/mod.rs:635-703`）对每个环境调用 `claude mcp list`。
- `claude_cli.rs:855` 在 `run_mcp_health_list` 里执行：
  ```rust
  fs::create_dir_all(config_dir)...
  ```

**后果（代码可直接推出，不依赖推测）**：

1. 从未启动过的环境，仅因为应用启动预热，就会被创建 `~/.claude-split/<env>/.claude`。
2. `shared_config::distribute_to` 用 `path.parent().is_dir()` 判断“环境是否启动过”（`shared_config.rs:917`）。目录被探测创建后，该环境会被当成“已启动”，后续分发会为它写 `.claude.json`。这直接违反了该方法注释里的“环境目录不存在（从未启动）时跳过，不凭空建文件”。
3. `claude mcp list` 会实际启动 stdio MCP 进程/建立远程连接；是否触发 OAuth 取决于具体服务。这是用户未打开 MCP 页时的外部副作用。
4. 同一逻辑还会在 MCP 页每次激活、并且距上次探测超过 30 秒时再次执行（`McpPanel.tsx:283-287`）。

**建议**：

- 预热阶段只加载只读列表，不探测；探测必须由用户点击“检测”或在页面 active 后显式触发。
- 健康探测不得创建环境目录；需要 `CLAUDE_CONFIG_DIR` 时，使用临时目录或先确认目录已存在。
- 把“探测”与“列表”拆成两个命令/两个 loading 状态，避免预热误触发。

## 四、P1：高影响问题

### P1-1 同步 Tauri 命令在 IPC/主线程做重 I/O

Tauri 2 的 `#[tauri::command]` 宏默认把同步函数放在 `ExecutionContext::Blocking`（本机 `tauri-macros 2.6.3` 的 `wrapper.rs` 默认值；`body_blocking` 直接执行函数体）。项目里对 `usage_stats`、`health_check`、`sync_all` 等已经用了 `spawn_blocking`，但下列命令仍是同步函数：

| 命令 | 重负载 |
|---|---|
| `list_mcp_services`（`mcp/mod.rs:382`） | `collect_state`：多次读文件、哈希、扫描死条目、共享覆盖 |
| `preview_mcp_change` / `apply_mcp_change`（`mcp/mod.rs:564,570`） | 同上 + 多文件事务写 |
| `cleanup_dead_project_entries`（`mcp/mod.rs:430`） | 扫描 + 多文件写 |
| `register_mcp_project` / `unregister_mcp_project`（`mcp/mod.rs:390,399`） | 写登记表 + 完整 `collect_state` |
| `plugins_overview`（`main.rs:2281`） | 读取所有环境插件账本并构造总览 |
| `environment`（`main.rs:2007`） | `detect_claude`：多个子进程/PATH 探测/登录 shell |
| `save_profile` / `delete_profile`（`main.rs:1450,1782`） | 全量扩展哈希 + MCP 分发 + 多文件回滚 |
| `import_cert*` / `clear_certs*`（`main.rs:2315,2321,2334,2340`） | 证书读写 + `install_integration`（全量扩展同步） |
| `restore_shared_mcp_entry`（`main.rs:2303`） | 写回 + `install_integration` |
| `export_diagnostics`（`health.rs:1007`） | 完整健康检查：并行 curl（每个网关最多 15s×2）+ Windows 每文件一次 PowerShell |
| `workbuddy_state`（`workbuddy.rs:1552`） | `find_executable`：PowerShell/注册表/快捷方式/进程扫描 |
| `list_mcp_update_info` / `set_mcp_update_check`（`mcp/mod.rs:707,724`） | 完整 `collect_state` |

**影响**：重 I/O 或网络时，IPC 调用线程被占用，界面表现为按钮无响应/窗口卡顿；`export_diagnostics` 在多网关+多凭据文件时可达数十秒。

**建议**：所有含文件扫描、子进程、网络、哈希的命令统一改为 `async` + `tauri::async_runtime::spawn_blocking`（或 `#[tauri::command(async)]`）；保持纯内存/单文件小操作同步。为每个命令补“主线程不得做重 I/O”的源码守护测试。

### P1-2 每 2 秒一次的 Codex 同步监控

`codex_sync.rs:1007-1020`：

```rust
std::thread::spawn(move || loop {
    let state = collect_state(&paths, &instances);
    match auto_sync_all(&paths, &state) { ... }
    std::thread::sleep(Duration::from_secs(2));
});
```

`collect_state` 本身包含：

- 每个环境 `.claude.json` 至少 1 次读取；
- 每个项目 `.mcp.json` + `settings.local.json` 读取；
- `scan_dead_entries` 再读一遍所有环境文件并 `revision`；
- `shared_overrides` 再读共享 mcp/ledger/每个环境文件；
- 对每个项目键做 `canonicalize_dir`（文件系统调用）。

也就是说，**应用整个生命周期内每 2 秒做一次全量 MCP 状态扫描**，即使用户从未打开 MCP 页、没有任何同步目标。

**建议**：改为事件驱动（文件 mtime/revision 变化、MCP 变更命令触发）或至少 30–60 秒轮询；扫描时只读 revision/registry，不做死条目与覆盖分析；没有 selected target 时直接跳过。

### P1-3 每次 `claude <环境>` 启动/退出都全量同步

生成的 shell 函数在网关/登录分支前后各调用一次 `_ccm_sync`（`main.rs:613,679,681,689`），对应 `--sync` 分支（`main.rs:3447-3478`）执行：

1. `reconcile_shared_ca()`（读配置、扫描 CA bundle）；
2. `refresh_scripts_if_stale()`（读/比较/可能写整份脚本）；
3. `extensions::sync_all_locked()`：对每个 shared Skill/Agent 以及每个目标副本递归 `hash_entry`（`extensions.rs:412-459,577-695`），并**无条件** `save_state`（`extensions.rs:831`）；
4. `sync::sync_configs()` → `shared_config::distribute`：快照所有目标文件（`shared_config.rs:492-502`），读取/写入，并**无条件** `save_ledger`（`shared_config.rs:482`）。

**影响**：Skills/Agents 越多、环境越多，启动/退出越慢；每次都产生一次原子写+fsync；Windows 上 `_ccm_sync` 的 pre-sync 还是 `Start-Process -Wait`（`main.rs:735`）。

**建议**：

- 用“共享库版本号/台账 revision”做快速脏检查，未变化直接返回；
- `save_state` / `save_ledger` 只在内容变化时写；
- pre-sync 只做必要的配置检查，重活放到后台（post-sync 已经可以 `-NoWait`）；
- 对 `claude` 启动路径做性能基准测试（大量 Skills × 多环境）。

### P1-4 `collect_state` 与 `attach_sync_state` 的重复读取

`collect_state`（`mcp/storage.rs:2755-3369`）对同一批文件至少读取 3–4 次：

| 阶段 | 读取 |
|---|---|
| 主体 | 每个实例 `read_doc_with_revision`（2814） |
| 项目 | 每个项目 `read_doc_with_revision`（2968）+ `revision(settings)`（2973） |
| Local revision | 每个实例 `revision(&p)`（3040） |
| 死条目 | `scan_dead_entries` 每个实例再 `read_doc` + `revision`（2450-2457） |
| 共享覆盖 | `shared_overrides` 再读共享 mcp、ledger、每个实例文件（3384-3408） |

`codex_sync::attach_sync_state`（`codex_sync.rs:501-573`）又对每个 service 调用 `read_target(&path)` 和 `revision(&path)`（525-526,564）；如果 50 个服务共享同一个 `~/.codex/config.toml`，这份 TOML 会被解析/哈希 50 次。

**建议**：一次扫描内缓存“路径 → (document, revision)”，复用给死条目/覆盖/同步目标；`attach_sync_state` 按 target path 分组，只解析一次。

### P1-5 用量扫描：缓存无淘汰、活跃文件全量重读、符号链接递归

- `usage_cache()` 是全局 `Mutex<HashMap<PathBuf, UsageFileCache>>`（`main.rs:3127-3132`），只插入、从不删除。文件删除/环境删除后条目永久保留；每个条目还保存完整 `rows`/`convs`。
- `parse_usage_file` 用 `fs::read_to_string` 读入整个文件再逐行解析（`main.rs:3220-3224`）。活跃会话文件每次 mtime/size 变化都会重读/重解析整个文件；Insights 页默认 30 秒刷新（`App.tsx:360-369`）。
- `newest_modified`（`main.rs:106-124`）和 `collect_jsonl`（`main.rs:3104-3115`）都用 `path.is_dir()` 递归，没有 `symlink_metadata`、没有 visited 集合、没有深度限制；项目历史目录里的符号链接环会导致无限递归/栈溢出。

**建议**：按字节偏移增量解析活跃 jsonl；缓存按路径 + 最近访问时间淘汰；扫描时跳过 symlink，或维护 visited set + 深度上限。

### P1-11 IPv6 loopback 被 API 配置误拒

`chatgpt/api_config.rs:124-142`：

```rust
let local = matches!(url.host_str(), Some("localhost" | "127.0.0.1" | "::1"));
```

`url` crate 的 `host_str()` 对 IPv6 返回带方括号的形式（本机 `url-2.5.8` 文档明确写 “IPv6 addresses are given between `[` and `]` brackets”）。因此 `http://[::1]:port` 的 `host_str()` 是 `"[::1]"`，`local=false`，会被拒绝；而 `main.rs:497-511` 的 `transport_is_loopback_or_secure` 是接受 IPv6 loopback 的，两套判定不一致。

**建议**：改用 `url.host()` 的 `Host::Ipv6(ip)` 判定（或接受 `"[::1]"`），与 `transport_is_loopback_or_secure` 共用同一函数；补 `[::1]` 测试。

### P1-13 MCP 健康输出按整行匹配状态

`mcp/mod.rs:755-816`：


### P1-14 `clean_leftover` 可能删除并发写者的临时文件

`mcp/storage.rs:833-851`：


`hash` 只由目标路径决定，同目标的所有写者共享前缀。若两个写者并发（例如两个 Project 级 apply，Project 变更不持配置锁；见 `mcp/mod.rs:576-583`），后进入者会在 `clean_leftover` 里删除前一个写者尚未 rename 的临时文件，导致其写入失败或读到不完整状态。

### P1-19 插件包下载的 SSRF/资源边界仍有窗口

`extensions.rs:1758-1837` 做了公开 HTTPS、私有地址拒绝、重定向校验，这是好的。但仍有两个边界：

1. **DNS rebinding**：`validate_plugin_package_destination` 在请求前解析域名并检查 IP（`1823-1835`），但 `reqwest` 在真正连接时会重新解析；恶意 DNS 可以先返回公网 IP 通过校验，再返回私网 IP 连接。要彻底防护需要自定义 resolver/连接固定 IP。
2. **解压体积**：`extract_plugin_package` 用 `entry.size()` 的**声明值**累加（`1903-1906`），`std::io::copy` 实际写出的字节数没有再次累计；构造不一致的 ZIP 仍可能突破 256 MiB 声明上限。`MAX_PLUGIN_PACKAGE_FILES` 同样基于 `archive.len()`。

**建议**：连接阶段使用 pinned resolver；解压时按实际写入字节累计并中止；对总文件数/单文件大小/压缩比设置更严格上限。

### P1-20 ChatGPT 私有网关 TLS 策略可能误拒公有 CA

`chatgpt/api_config.rs:229-243` 和 `bridge.rs:238-250`：

```rust
if private_gateway {
    builder = builder.tls_certs_only(certs);
} else {
    for cert in certs { builder = builder.add_root_certificate(cert); }
}
```

只要用户导入过任意 CA（union bundle 非空），连接私有地址网关时就会**只信任导入的 CA**，不再信任平台根。若该私有网关使用的是公有 CA（例如内网 DNS 指向公网证书），会被拒绝；若导入的 CA 与它无关，也会被拒绝。WorkBuddy 的 `gateway_client` 则始终使用“平台根 ∪ 额外根”（`workbuddy.rs:2447-2449`），两套语义不一致。

**建议**：默认使用 `add_root_certificate`（平台根 ∪ 导入 CA）；仅在用户显式选择“只信任导入 CA”时使用 `tls_certs_only`，或先在平台根失败后再尝试导入 CA。

### P1-21 兼容桥接的上游错误正文只替换当前 Key

`chatgpt/bridge.rs:568-575`：

**建议**：统一调用 `redact_gateway_text(&body, Some(key))`，再截断。

### P1-22 `PluginCommandQueue` 在多目标任务中会整单丢弃

`pluginTasks.ts:74-76`：

```ts
if (keys.some((key) => this.pending.has(key))) return Promise.resolve();
```

注释说“Serialize writes without blocking actions for unrelated plugins”，但：

- **失败可解释**：大量 `Result` + 具体错误文案 + 警告汇合（`compose_sync_report`、`DistributeReport`），比“静默成功”好得多。
- **测试密度**：后端 417 个测试，覆盖锁协议、事务回滚、CA 迁移、路径安全、用量去重、ChatGPT 进程隔离等。

### 5.2 结构性问题

#### （1）多套“原子写”实现，语义不一致

| 实现 | 文件 | 特点 |
|---|---|---|
| `sync::write_bytes_atomic` | `sync.rs:670-707` | 临时文件 + sync_all + rename + 0600 |
| `mcp::write_json_transactional_inner` | `mcp/storage.rs:873-952` | 备份轮转 + rollback rename + revision + 0600 |
| `workbuddy::write_text_atomic` / `write_document` | `workbuddy.rs:302-311,1458-1495` | 唯一临时名 + backup/previous + 0600 |
| `codex_sync::write_text_atomic` | `codex_sync.rs:643-699` | 唯一临时名 + rollback + 0600 |
| `main::save_to` / `save_settings_value` | `main.rs:411-482,1337-1346` | 两阶段备份；无 fsync |
| `health::export_diagnostics` | `health.rs:1026` | 直接 `fs::write` |

这导致：是否 fsync、是否保留备份、失败回滚粒度、权限收紧、临时文件清理策略各不相同。建议抽一个 `atomic_io` 模块，按 `{fsync, backup, revision, permissions}` 选项复用。

#### （2）PEM / 指纹 / revision 重复

- `main::pem_blocks/norm_pem/has_block/cert_fingerprint`（`main.rs:2119-2142,335-338`）使用“去所有空白”的 SHA-256。
- `workbuddy::pem_blocks/pem_certificates/normalize_pem`（`workbuddy.rs:314-329,1234-1249`）只去 CR/LF，指纹用 `content_hash`。
- `mcp::revision` 与 `workbuddy::revision` 使用 `DefaultHasher`（`mcp/storage.rs:424-452`、`workbuddy.rs:901-911`），而 `main::content_hash` / Codex 同步已经明确改用稳定 SHA-256（`main.rs:2769-2776`、`codex_sync.rs:185-196`）。

  **风险**：MCP/WorkBuddy 的 revision 目前只在单次进程内比较，尚未持久化；但如果将来持久化或跨版本复用，`DefaultHasher` 不保证稳定会导致“所有条目都冲突”。建议统一为 SHA-256 内容哈希。

#### （3）主题色三处定义

- `main.tsx:30-48` 的 `THEME_COLORS`（Mantine palette）
- `themeScheme.ts:32-50` 的 `THEME_DEFINITIONS`（预览色）
- `glass.css:56-141` 的 `html[data-theme=...]`（实际 CSS 变量）

三者没有自动一致性校验；例如 `glacier` 的 `themeScheme` deep 色与 CSS `--theme-deep` 并不相同。删除的 `glassCss.test.ts` 曾覆盖部分布局，但主题一致性没有替代护栏。

#### （4）前后端 API 契约手工镜像

`api.ts` 853 行手工定义 90+ 命令与类型；Rust 侧有 camelCase、snake_case、kebab-case 三种序列化风格（例如 `Profile` camelCase、`EnvInfo` snake_case、`McpEffectiveState` kebab-case）。`api.test.ts` 只覆盖 `detect_models` 一个命令。建议用 `ts-rs`/schemars 生成类型，或至少为每个命令加参数/返回字段契约测试。

#### （5）单文件过大

| 文件 | 行数 | 说明 |
|---|---|---|
| `src-tauri/src/mcp/storage.rs` | 6,486 | 生产逻辑约 3,500 行 + 测试 |
| `src-tauri/src/main.rs` | 5,991 | 配置、shell 生成、CA、探测、用量、启动全部混在一起 |
| `src-tauri/src/workbuddy.rs` | 3,583 | 发现、配置、CA、HTTP、进程启动 |
| `src-tauri/src/extensions.rs` | 2,986 | 资源分发、插件 CLI、ZIP、迁移 |

建议按职责拆分（`shell_integration.rs`、`ca.rs`、`gateway_probe.rs`、`usage.rs`、`app_setup.rs`），测试移到 `tests/` 或独立 `*_tests.rs`，降低单文件认知负担。

#### （6）死代码 / 隐藏入口

- `sync::migrate_shared_resources_once` 标记 `#[allow(dead_code)]`（`sync.rs:61-73`），生产路径没有调用；`master_dir` 仅测试使用（`sync.rs:160-166`）；`ensure_links_in`/`migrate_dir` 仅在 `cfg(test)`。
- `health::startup_health_check`（`health.rs:694-709`）已注册到 `invoke_handler`（`main.rs:3590`），但前端从未调用（`securityClaims.test.ts` 甚至断言 App 不含 `startupHealthCheck`）。这是一个隐藏的、会解密凭据并访问网络的 IPC 入口，建议删除或明确标注仅供内部。
- `mcp::validation::RESERVED_NAMES` 里的 `"Claude Preview"`/`"Claude Browser"` 因空格在字符集校验阶段就被拒绝，永远不会命中保留名分支（`mcp/validation.rs:11-17,49-64`）。

#### （7）并发/锁矩阵

现有锁：

- `sync::config_lock`（文件锁 + 心跳）；
- `mcp::codex_sync::WRITE_LOCK`（进程内 Mutex）；
- `workbuddy::WRITE_LOCK`（进程内 Mutex）；
- `chatgpt::OPERATIONS`（进程内 Mutex）。

未受锁保护的 read-modify-write：

- `mcp::register_project` / `unregister_project`（`storage.rs:608-636`）读登记表 → 改 → 写，没有 revision/锁；两个并发 IPC 会丢更新。
- `mcp::update::set_update_check`（`update.rs:552-571`）同样。
- `workbuddy::managed-certs.json` 的 `record_managed_certs` / `prune_managed_certs`（`workbuddy.rs:467-517`）不在 `WRITE_LOCK` 内；CA 导入与清理可能并发覆盖。
- `health/config` 读写大多通过原子 rename，单文件安全，但跨文件快照不一致。

建议为这些路径补锁或 CAS（compare-and-swap），并在文档中画出锁顺序，避免未来死锁。

### 6.2 I/O 放大（可由代码直接计数）

- `list_mcp_services` 一次调用：对 N 个环境，至少 3N 次 `.claude.json` 读取 + 3N 次哈希；项目多时更多。
- `attach_sync_state`：对 M 个 service，`read_target` M 次、`revision` M 次；若共享同一个 `config.toml`，同一文件被解析 M 次。
- `codex_sync` 监控：每 2 秒重复上述完整扫描。
- `--sync`：每次 `claude` 启动/退出各一次全量扩展哈希。

### 6.3 内存与磁盘增长

- `usage_cache` 无淘汰（`main.rs:3127-3132`）。
- `sync.log` 无轮转（`sync.rs:479-492`）。
- ChatGPT `batches/*.json`、`transfers/*.json`、插件 marketplace 目录无清理。
- 主题资源 10 个 PNG 共约 **13 MB**（实测 873 KB–1.44 MB/个）；`dist/` 总计约 15 MB。`glass.css` 生产 CSS 约 378 KB。这些会直接进入安装包和运行时内存/解码开销。

### 6.4 前端

- 所有 9 个页面在启动后 0–3.1 秒内被 `PersistentPage` 挂载并保留；多个页面 mount 时各自加载数据（见 P1-6）。
- `ChatGptPanel` 15 秒轮询；`McpPanel` 激活探测；`UsagePanel` 30 秒自动刷新（Insights 页打开时）。
- ECharts 懒加载 chunk 约 587 KB；主 `index` JS 约 272 KB，CSS 378 KB，整体可接受；主题 PNG 是主要体积来源。

### 6.5 优化优先级

**低风险快速收益**：

1. 预热页面不加载数据/不探测（只挂载 UI）。
2. `collect_state` 内复用 `(path, document, revision)` 缓存；`attach_sync_state` 按 target 分组。
3. `save_state`/`save_ledger` 内容不变不写。
4. 监控线程改为 30–60 秒或事件驱动。
5. 压缩主题 PNG 为 WebP/AVIF（预计可减少 70–90%）；必要时延迟加载。
6. `recent_sync_log`/诊断导出只读文件尾部（`seek` 到末尾），而不是整文件 `read_to_string`。
7. `usage_stats` 增量解析 + 缓存淘汰。

**结构性收益**：

1. 统一 `atomic_io` 与 revision/hash。
2. 重命令全部 `spawn_blocking`。
3. 前端共享 profile/runtime/verification 数据源，去掉 `App`、`ConfigPanel`、`CaCertButton`、`EnvironmentProof` 的重复 `listProfiles`/`profileRuntimeInfo` 调用。
4. 将 `main.rs` 拆分并引入命令层/领域层边界。

### 8.2 跨平台缺口/风险

1. **`powershell` 硬编码**：`ps_command` 只用 `powershell`（`main.rs:1416-1427`）；Windows 11 若禁用 Windows PowerShell 5.1，所有依赖它的功能（健康检查 ACL、WorkBuddy 证书、DPAPI 兼容测试）会失败。应回退到 `pwsh`。

3. **IPv6 loopback**：见 P1-11，跨平台都会遇到。
4. **文件权限模型不对称**：Unix 显式 0600，Windows 依赖用户目录继承 ACL。代码和 UI 已说明威胁边界，但“权限检查”在 Windows 上只对部分文件执行 PowerShell ACL 查询，且存在 `is_file` fail-open。

7. **PowerShell 脚本的 BOM**：`generate_ps1` 明确加了 UTF-8 BOM（`main.rs:714`），这是正确的；保留。

## 十二、一句话总结

PathMux 的底层安全/事务设计值得肯定，但当前最需要的是**把“凭据不出后端、探测不主动发生、重活不占主线程、名字不破坏脚本”这四条变成架构级不变量**；否则随着 Skills/环境/MCP 数量增长，启动与操作延迟、凭据暴露面和跨平台差异会先于功能问题暴露出来。
