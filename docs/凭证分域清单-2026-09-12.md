## 一、结论速览（三句话）

1. **只有一个凭证用了系统安全存储**：Claude 网关 API Key（macOS 钥匙串 / Windows DPAPI）。**它不是** Windows 凭据管理器，是自家 DPAPI 加密。
2. **WorkBuddy 的 Key（系统/员工/模型级）和 MCP 的 env/header 密钥在两个平台都是明文文件**，不被任何「钥匙串/DPAPI」承诺覆盖。
3. **Windows 上有三处与 macOS 不等价**：配置文件无权限限制、`clear` 是空操作、启动 WorkBuddy 时少了 CA 环境变量注入。

### 2.4 其他

- **Claude 账户登录态**（`type == "account"`）：只做存在性判断，全仓**无**读取/解密 OAuth token 的代码（`main.rs:1224-1225` 仅 `is_file()`）。
- **删除回滚缓冲**：只有 macOS 会把 key 解密进内存做回滚（`deletion_credential_backup`），

## 四、Windows / macOS 不等价清单（P0-A#4 第三块）

| # | 差异 | 位置 | 影响 |
|---|---|---|---|
| 1 | WorkBuddy 明文配置：macOS 显式 `0600`；**Windows 不设，靠继承** | `workbuddy.rs:951-956` **[已核实]** | 见下方实测更正 |
| 2 | `credentials::clear` 在 Windows 是**空操作** | `credentials.rs:145-148` **[已核实]** | 删除实例时密钥密文只能靠重写 `config.json` 清掉 |
| 3 | 启动 WorkBuddy **不注入 `NODE_EXTRA_CA_CERTS`** | `workbuddy.rs:1940-1944` **[已核实]** | macOS 少一条 CA 生效路径 |
| 4 | `import_workbuddy_ca` Windows 会 `certutil -user -addstore -f Root`（`workbuddy.rs:1370`），macOS 分支只同步 CLI bundle，**不动系统信任库**（`workbuddy.rs:1396-1402`） | 同上 | 「装一次全机信任」只在 Windows 有 |
| 5 | WorkBuddy 可执行文件探测：Windows 有注册表（`workbuddy.rs:605-609`）与快捷方式（`616-621`）两个来源，macOS 两者都返回 `None` | 同上 | macOS 只剩「运行中」与「常见路径」两条 |
| 6 | Windows 无 Key 回滚能力 | `main.rs:1072-1075` | 删除实例失败时无法恢复 key |

**第 3 条的边界**：`sync_workbuddy_ca_bundle` 在**两个平台**都会把 CA 合并进 WorkBuddy CLI 自带的 `ca.pem`（`workbuddy.rs:1924-1926`）。所以 macOS 并非完全没有 CA 路径，而是**少了一条**（环境变量注入）。那条路径是否足够，**本机无 Mac，未验证**。

### 更正：第 1 条「Windows 无权限限制」的措辞（2026-09-12 实测）

本文档初版把第 1 条写成「Windows 上同机其他用户可读密钥」。**这是未经验证的推断，实测后推翻。**

本机 `icacls` 实测 `~/.cc-manager/config.json`（它建在用户主目录下，与 WorkBuddy 配置同源）：

```
<计算机名>\CodexSandboxUsers:(I)(RX)     ← 第三方工具创建的本地组
NT AUTHORITY\SYSTEM:(I)(F)
BUILTIN\Administrators:(I)(F)
<计算机名>\<用户名>:(I)(F)               ← 本人
```

`(I)` 表示**继承**自用户主目录。即 Windows 侧**并非「无保护」**：在标准机器上，用户主目录默认只授予本人 + SYSTEM + Administrators。

### 威胁边界定义（2026-09-12 用户裁定，本文档所有权限结论以此为准）

> **本产品用文件权限防御的威胁是：防止同机上的其他普通用户读取凭证文件。**
> **管理员、SYSTEM、root、以及任何具备 sudo / 提权能力的主体，不属于文件权限能够可靠防御的范围** —— 它们在两个平台上都能绕过文件权限。任何文案与判断都不得暗示能防住这类主体。

**据此的等价验收目标**：Windows 与 macOS 要达成的是**安全语义等价**（"其他普通用户读不到"），**不是权限位或 ACL 形式相同**。

| 平台 | 机制 | 对「其他普通用户」 | 对管理员 / SYSTEM / root |
|---|---|---|---|
| macOS | 显式 `0600` | 读不到 | **能读**（sudo / root） |
| Windows | 继承用户目录 ACL | 读不到（实测见上） | **能读**（Administrators / SYSTEM 继承 `(F)`） |

**关键更正**：本文档初版曾把 macOS 写成"连其他管理员也读不到"。**这是错的** —— `0600` 同样挡不住 root 或具备 sudo 的管理员。两个平台在这条威胁上的实际安全性**是等价的**，差别只在"显式设置 vs 依赖继承"，而非"谁更强"。

因此第 1 条**降级为形式差异，不作为 P0 阻塞项**。用户裁定：暂不引入 `icacls` 或新的 ACL crate；若将来要做显式 DACL，优先用**现有 windows-sys** 能力，不走 shell-out —— 那属于纵深加固。

## 五、§四 六条不等价的**逐条判定**（2026-09-12 收口）

| # | 判定 | 依据 |
|---|---|---|
| 1 | **已降级，非阻塞** | 用户裁定威胁边界只到"同机其他普通用户"，Windows 继承 ACL 已覆盖；显式 DACL 属纵深加固 |
| 2 `credentials::clear` Windows 空操作 | **不是缺陷** | Windows 的密钥从未离开 `config.json`（DPAPI 密文 = `token_enc`），**没有独立凭据库可清**。密文一共三处落点：`config.json`、它的备份族、内嵌密文的 `cc.ps1` —— 删除时分别由 `save(&next)`、`scrub_profile_from_config_artifacts`、`refresh_existing_integration_scripts` 重写。已有测试断言产物族中无密文；**本次新增** `deleted_profile_ciphertext_is_gone_from_the_generated_script` 补上第三处（带对照断言，防空跑） |
| 3 启动 WorkBuddy 不注入 `NODE_EXTRA_CA_CERTS` | **已由后续改动覆盖** | ③-2 给 macOS 加了 `open --env`，两个平台都注入了。真机是否真进进程仍需 macOS 验证（见清单 §四组） |
| 4 `import_workbuddy_ca` macOS 不动系统信任库 | **判定：不再需要**，但**留一条无法本机确认的疑点** | CA 的三条生效路径都不依赖系统信任库：Node 走 `NODE_EXTRA_CA_CERTS`、应用自身 reqwest 走 `union_ca_bundle_path()`（F6）、WorkBuddy 走合并后的 `ca.pem`。**但 WorkBuddy 自己的 GUI 若走 Chromium 的 OS 信任库，macOS 侧就会缺这一环 —— 本机无 Mac、也没有 WorkBuddy，无法确认** |
| 5 WorkBuddy 可执行文件探测源不对称 | **可接受** | macOS 少了注册表/快捷方式两个来源，仍有「运行中进程」+「常见路径」，且**有手动选择兜底**。要补齐需在 macOS 上加 Spotlight(`mdfind`) 之类来源，属能力增强、非缺陷 |
| 6 Windows 无 Key 回滚 | **不是缺陷** | Windows 侧 `deletion_credential_backup` 返回 `None` —— 因为它**没有东西需要回滚**：密钥随 `config.json` 一起被删除快照还原。macOS 侧有 `deletion_credential_backup` + 失败时 `store_token` 恢复 |

**结论**：六条里 #1/#2/#3/#6 已判定收口，#5 判定为可接受的能力差异，
**只有 #4 还挂着一个"本机无法确认"的疑点**（WorkBuddy GUI 在 macOS 上是否依赖系统信任库）
—— 已并入 macOS 真机验证清单，属**验证**而非开发。
