# 对外开放产品战略与产品化路线

> **分析日期**：2026-09-11
>
> **版本基线**：v2.3.8（commit `5a33531`）
>
> **目标**：判断 并路 PathMux 从内部工具走向公开软件的产品方向、优先级与发布门槛
>
> **对照文档**：[`全局产品分析与优化方向-2026-09-11.md`](./全局产品分析与优化方向-2026-09-11.md)
>
> **约束**：本轮仅分析，不修改应用代码；不把静态代码、工作流配置或单平台验证扩大为双平台实机结论

## 一、执行摘要

### 1.1 产品判断

这个项目已经不是一个简单的 profile switcher。它实际覆盖了 Claude Code 多环境隔离、账号与第三方网关、模型档位、终端入口、MCP、跨实例扩展共享、Codex 同步、本地用量、诊断、备份恢复、证书和 WorkBuddy。技术深度明显超过其当前品牌、文档和首次体验所表达的范围。

但公开产品不能仅靠“功能很多”成立。当前最有机会建立的核心价值不是复制 CC-Switch 的供应商广度，而是：

> **让同时使用个人 Claude 账户、公司路由和多个项目配置的开发者，在同一台电脑上并用多个环境而不串号、不串配置，变更可解释，出错可恢复。**

“安全隔离与可验证恢复”比“支持更多模型”更接近当前代码已经形成的能力优势。MCP 的 preview、revision、脱敏、事务写入和回滚，以及主配置损坏恢复、环境删除回滚和诊断能力，构成了真实但尚未被产品化表达的可靠性资产。

### 1.2 当前结论

| 判断 | 结论 |
|---|---|
| 是否值得继续产品化 | **是**，核心问题真实，已有实现具备差异化基础 |
| 是否应立即正面复制 CC-Switch | **否**，广度竞争会稀释现有优势并放大维护面 |
| 是否可立即作为稳定公开产品广泛发布 | **否**，安装信任、安全承诺、内部默认值、macOS 实机证据和治理仍存在阻塞 |
| 下一阶段合理形态 | 面向明确人群的受控 Preview，而不是无门槛 Stable |
| 产品北极星 | 成功建立且持续使用的“隔离环境”，并能证明切换正确、配置未串线、故障可恢复 |

### 1.3 最重要的五项决策

1. **把目标用户收窄**：先服务同时使用个人账户、公司网关和多个项目配置的 Windows/macOS 开发者，而不是所有 AI 工具用户。
2. **把可靠性变成界面能力**：从“底层有备份”升级为用户看得懂的变更预览、结果、警告、恢复点和撤销入口。
3. **先补信任链再拉新**：OS 级签名/notarization、TLS 行为、凭证范围、诊断隐私和双平台证据是公开化门槛，不是发布后的润色项。
4. **把 WorkBuddy 模块化**：保留能力，但从所有用户的一级主任务降为可选组织集成，并清除内部网络默认值。
5. **建立证据驱动发布制**：代码实现、自动测试、CI、真实设备验证和公开承诺分层管理，任何一层都不能替代另一层。

## 二、分析方法与证据等级

本文综合阅读前端、Rust 后端、测试、CI、Release、README、MCP 方案、旧产品分析和 Windows 桌面实机记录。为避免把推断写成事实，后文使用四级证据：

| 等级 | 含义 | 可用于什么结论 |
|---|---|---|
| A｜实机证据 | 在真实 Tauri 桌面应用中完成并记录 | 仅限记录覆盖的平台和旅程 |
| B｜自动化证据 | 有测试或工作流覆盖 | 证明被测逻辑，不等于真实设备体验 |
| C｜代码事实 | 静态实现可确认 | 说明当前行为设计，不保证环境中必然成功 |
| D｜产品假设 | 用户需求、市场或价值推断 | 必须通过访谈、遥测或实验验证 |

本轮可确认的验证边界：Windows 已有真实 Tauri/WebView2 实机记录；macOS 有代码分支、自动化矩阵和钥匙串测试配置，但没有本轮可引用的真实设备端到端记录。CI 文件存在不代表当前提交在本轮已经运行并通过。本轮没有代码变化，因此未重跑产品开发门禁。

## 三、当前产品事实：能力比定位更成熟

### 3.1 用户今天实际得到什么

核心链路可归纳为五层：

1. **环境隔离**：主账户、独立账户和第三方路由分别使用独立 `CLAUDE_CONFIG_DIR`。
2. **终端切换**：通过 Windows PowerShell 或 macOS/Unix shell 集成执行 `claude <环境名>`，并对调用环境变量做作用域控制或恢复。
3. **配置收敛**：共享 Skills、Plugins、Agents、Commands，并对 MCP 和 enabledPlugins 做多副本合并。
4. **安全变更**：MCP 已具备 preview、确认、revision 冲突检测、敏感字段脱敏、事务写入、备份和回滚。
5. **观察与恢复**：本地会话用量、健康检查、同步日志、诊断导出、配置备份、损坏文件保留和环境删除回滚。

这些能力共同指向“本地 AI 开发环境控制面”，但界面和 README 仍主要把它讲成给同事安装的 Claude 管理工具，造成产品价值被低估、使用边界被高估。

### 3.2 已形成的产品资产

- **隔离不是视觉分组，而是运行时配置目录和环境变量隔离。**
- **写入安全有真实机制。**主配置和 MCP 均采用临时文件、备份、revision 或回滚策略；环境删除还有 staging 和残留核验。
- **MCP 是全项目最成熟的变更范式。**其“预览—确认—应用—冲突—警告”应成为全产品标准，而不是孤立亮点。
- **诊断并非纯静态检查。**它会并发探测 router 的模型接口，也会检查 CLI、终端集成、共享链接、本地 CA 文件数量和固定模型设置；这不等于确认系统证书链或严格 TLS 已受信。
- **本地优先基础明确。**用量来自本地 Claude 会话 JSONL，配置与备份主要位于本机，没有发现当前产品依赖中心云账户才能工作。
- **扩展市场克制是正确的。**当前明确不承担第三方扩展市场和安装责任，避免过早引入供应链与审核负担。

### 3.3 能力强但产品表达弱的断层

| 底层已有能力 | 用户当前感知 | 应升级的产品表达 |
|---|---|---|
| 原子写入、备份、损坏保留 | “保存成功/失败” | 最近变更、恢复点、影响范围、可撤销状态 |
| MCP revision 与脱敏 diff | 只在 MCP 看到 | 推广到同步修复、证书、WorkBuddy 和高风险设置 |
| 环境隔离 | 用户记命令和环境名 | 明确显示当前身份、路由、配置目录与切换证明 |
| 健康检查 | 一组健康项 | 形成“连接—隔离—恢复—平台”证明链 |
| 本地用量 | Token 图表 | 清楚区分本地遥测、真实处理量、账单和估算费用 |

## 四、目标用户、核心任务与定位

### 4.1 推荐首要用户

首要用户不是泛化的“开发者”，而是同时满足以下两项以上的人：

- 有个人 Claude 账户，同时需要公司或团队网关；
- 维护多个客户、项目或安全边界不同的 Claude Code 配置；
- 经常切换模型路由，但不愿手工修改环境变量和 settings；
- 害怕把公司凭证带入个人项目，或把个人会话带入公司环境；
- 已经遇到 MCP、插件或 settings 多副本冲突；
- 需要在 Windows 与 macOS 团队内提供可诊断、可恢复的统一流程。

次要用户可以是只使用多个第三方网关的个人重度用户；WorkBuddy 用户属于组织集成用户，不应默认等同于所有 Claude Code 用户。

### 4.2 核心 Job to Be Done

> 当我在个人账户、公司路由和多个项目之间工作时，我希望快速确认“现在用的是谁、请求去哪里、加载哪份配置”，并能在变更出错后恢复，从而避免串号、串配置和不可解释的故障。

围绕这一任务，产品必须给出四种证明：

1. **连接证明**：CLI 和目标端点确实可用；模型列表探测只作为接口证明，不冒充完整能力证明。
2. **隔离证明**：当前账户、路由、配置目录、模型档位和项目作用域清晰可见。
3. **恢复证明**：变更前有什么、变更后影响什么、失败如何回滚、用户如何恢复。
4. **平台证明**：Windows 与 macOS 各自支持哪些 Shell、凭证、证书、安装和启动路径，并有对应证据。

### 4.3 推荐定位语

**短定位：**

> Claude Code 多环境隔离与可靠变更中心。

**面向用户的价值主张：**

> 在个人账户、公司网关和项目配置之间安全切换；每次变更看得见，发生故障退得回。

这比“并路 PathMux”更具体，也比“用 Claude Code 的壳跑其他模型”更稳健。后者只描述一种现象，无法覆盖官方账户、配置隔离和恢复价值，并容易把产品拖入纯供应商数量竞争。

### 4.4 明确不做

- 现阶段不追求最多 provider preset。
- 不立即扩展为 Claude、Codex、Gemini 等所有 AI 工具的统一超级客户端。
- 不建设第三方插件或 Skill 市场。
- 不在没有价格来源和账单对账前宣称“真实成本”。
- 不在缺少证据时宣称“企业级安全”“所有凭证均进入系统安全存储”“零数据外发”或“Windows/macOS 完全等价”。
- 不先建设复杂的团队云、权限体系和企业 SaaS 管理后台。

## 五、对旧文档的深度评审

旧文档适合作为 v2.3.8 的问题审计基线：它抓住了切换、同步、诊断三条闭环，识别了 CA 后续集成吞错、Codex 持久化哈希、快照恢复、危险操作、FTUE、术语和文档漂移等重要问题。但它不宜原样作为公开产品路线图，原因有三点：部分事实需勘误，部分风险分级过宽，功能问题与公开化门槛尚未分层。

### 5.1 应保留的判断

- 多身份/多网关切换仍是当前最接近核心的入口。
- 核心切换失败缺少足够可见性，Shell 支持范围也没有被产品明确表达。
- CA 导入或清空后重建集成脚本的错误被丢弃，却仍可能向用户返回成功，这是典型“错误成功”。
- Codex 同步把 `DefaultHasher` 结果持久化并用于后续状态判断，存在跨构建稳定性风险。
- 同步的删除传播存在缺陷：**被跳过的副本会被踢出快照 `replicas` 名单，其残留 key 随即被 Upsert 复活并写入快照固化**（触发条件已于 2026-09-12 查实并修正，非「快照丢失」——详见 §10 P0-B #13）。
- MCP 与其他危险变更的交互保障不一致。
- 首次使用、术语、README、Guide 和发布流程存在状态漂移。
- 本地用量尚不能回答跨网关费用、预算和账单问题。
- 底层恢复能力尚未形成统一的用户恢复中心。

### 5.2 必须勘误或降级的判断

| 旧文档表述 | 修正结论 | 原因 |
|---|---|---|
| 诊断不检查网关通不通 | **事实错误**：健康检查会并发调用 router 模型检测 | `health.rs` 已有 router 探测路径 |
| macOS zsh/bash 标记为已支持 | 应写为**代码存在，实机未验证** | 写入配置不等于真实 Shell 全链路通过 |
| 任意 Shell 的未知实例都应被产品拦截 | 当前 wrapper 架构只能在已加载集成的 Shell 中拦截 | 未加载 wrapper 时上游 `claude` 不受本产品控制 |
| Windows Terminal 与 cmd、PowerShell 并列 | Windows Terminal 是宿主；应按其中运行的 Shell 分类 | 支持对象应是 PowerShell、cmd、Git Bash 等 |
| DefaultHasher 均属同等级高危 | 重点是 Codex **持久化且跨版本参与决策**的 hash | storage revision 多用于短生命周期冲突检查，路径 hash 后果也不同 |
| 缓存差异可推导成本相差一个数量级 | 只能得出“遥测显著不同，值得验证” | 私有样本未去重，且缺价格、账单和同任务对照 |
| CA 是所有新用户的固定首用步骤 | CA 只适用于需要自签公司网关的分支 | 官方账户和公共可信网关不应被强制引导安装 CA |
| WorkBuddy 与 MCP 零交集，等于三个产品 | 主任务独立，但共享配置、证书、诊断和启动语境 | 更合理结论是可选模块，而非立即拆成独立产品 |
| 前后端脱敏规则同源 | 当前是两份实现规则对齐，不是共享代码源 | 后续仍存在漂移风险 |
| 双平台 CI 门禁已生效 | 只能确认 workflow **已配置** | 未读取对应运行结果，不能宣称当前提交已通过 |

### 5.3 路线图为何要重排

旧文档将费用、能力矩阵等价值扩展与公开发布阻塞混在同一优先级体系中。对于内部工具，这种排序尚可；对于公开产品，必须先解决安装信任、凭证承诺、TLS、内部默认值、治理和跨平台证据。否则新增成本看板只会把更多用户引向一条尚未建立信任的分发链路。

## 六、与 CC-Switch 的竞争定位

> **外部证据口径**：本节依据 2026-09-11 对 `farion1231/cc-switch` 公开仓库、README 与公开 Release（当时最新可见版本 v3.20.2，发布日期 2026-09-07）的定点检查，用于功能定位比较；未审计其内部实现、商业数据、活跃用户或留存，因此不据此判断市场领先程度。

截至本分析日期，CC-Switch 的公开产品路线更接近“多 AI 工具桌面控制中心”：其公开资料展示了多个 AI 客户端、50+ provider presets、MCP、Skills、prompt、本地代理、failover/circuit breaker/health check、用量费用、云同步与多平台分发。这里的“优势”仅指公开功能覆盖广度和开箱可选项，不代表这些能力均经本轮实测。

### 6.1 不应正面复制的原因

1. **维护成本不对称**：每增加一个客户端或 provider，就引入配置格式、认证、兼容、版本漂移和支持成本。
2. **现有优势会被稀释**：本项目最强的是可靠写入和隔离，不是 provider catalog。
3. **公开信任基础尚未补齐**：在安装签名、隐私和双平台证据之前扩张功能，会扩大故障与承诺面。
4. **用户心智难以胜出**：如果比较维度只是“支持多少工具和供应商”，后来者很难形成明确理由。

### 6.2 推荐竞争维度

| 维度 | CC-Switch 倾向 | 本项目推荐方向 |
|---|---|---|
| 核心心智 | 多 AI 工具与 provider 切换 | Claude Code 多环境隔离与可靠变更 |
| 目标用户 | 多客户端、多供应商重度个人用户 | 个人账户 + 公司路由 + 多项目用户及小团队 |
| 功能取舍 | 广覆盖 | 深隔离、强解释、可恢复 |
| 变更模型 | 便利优先 | preview、revision、rollback、proof 优先 |
| 团队价值 | 同步和统一入口 | 配置边界、故障诊断、可审计恢复 |
| 扩张路径 | 增加工具和 provider | 增加可靠性适配器和受控组织集成 |

### 6.3 可形成的护城河

真正难复制的不是配置表单，而是长期积累的“变更安全模型”：

- 对配置来源、作用域和覆盖关系的正确建模；
- 对未知字段和新 transport 的保守保留；
- 对外部变更的 revision 检测；
- 对敏感数据的可解释脱敏；
- 对多文件事务、失败回滚和损坏文件的恢复；
- 对 Windows 与 macOS 平台行为的持续证据矩阵。

如果这些能力最终形成统一的用户体验和测试资产，产品可从“切换工具”升级为“AI 开发环境的可靠控制面”。

## 七、用户旅程与信息架构重构

### 7.1 首次使用不应是一条固定流水线

现有空态主要让用户直接“新建环境”，但公开产品需要先识别意图，并按场景分支：

**分支 A｜官方或独立账户**

1. 发现并验证 Claude CLI；自动失败时允许手动选择。
2. 创建独立登录环境并解释配置隔离。
3. 安装当前平台和 Shell 的终端入口。
4. 启动一次验证，明确展示当前环境和配置目录。

**分支 B｜公共可信第三方网关**

1. 创建网关环境。
2. 验证 URL、凭证和模型列表接口。
3. 映射 Opus/Sonnet/Haiku 档位。
4. 启动验证，并明确模型列表成功不代表工具调用、上下文、缓存或计费全部兼容。

**分支 C｜自签公司网关**

> **前置依赖**：产品必须先提供默认启用的严格 TLS 探测，并能区分“证书链失败”与 DNS、TCP、鉴权或业务错误。当前模型检测固定使用 `insecure`，尚不能触发下述分支，因而该依赖属于 P0 验收项。

1. 完成分支 B。
2. 只有 TLS 失败且组织明确提供 CA 时，才进入证书引导。
3. 展示证书影响范围、平台差异和撤销方式。
4. 重建终端集成并复验；任何一步失败都不得显示整体成功。

首次成功标准不是“保存了一条配置”，而是用户完成一次可证明的启动，并理解当前身份、路由和配置边界。

### 7.2 推荐信息架构

**一级导航建议：**

1. **环境**：环境、账户、网关、模型档位、当前运行状态。
2. **连接与配置**：MCP、共享扩展和目标同步。
3. **洞察**：本地用量与未来经验证的费用/能力信息。
4. **健康与恢复**：诊断、同步警告、恢复点、证书和导出。
5. **设置**：应用更新、安全说明、隐私和平台集成。

WorkBuddy 建议进入“组织集成”或可选模块，不在未配置时占据所有用户的一级导航。Guide 不应只是独立页面，而应成为任务内上下文帮助和首次使用 checklist。

### 7.3 统一语言

建议统一使用“环境”作为用户对象；类型为“独立登录环境”和“网关环境”。“配置作用域”保留给 User/Local/Project，“组织”仅用于 WorkBuddy。避免继续混用环境、实例、环境、账户和网关。

每个环境详情页固定回答：

- 我现在是谁？
- 请求发往哪里？
- 使用哪份配置？
- 三个模型档位分别是什么？
- 哪些 Shell 可以启动？

## 八、信任、安全、隐私与公开分发

### 8.1 安装信任是 P0

当前 README 以绕过 Gatekeeper/SmartScreen 作为安装路径，Release 也把用户引回该说明；同时未见 Windows trusted publisher 签名和 macOS codesign/notarization 的明确配置。Tauri updater artifact 签名只保护更新包完整性，不等同于操作系统级发行者信任。

公开 Preview 前应完成：

- Windows 受信任代码签名和安装验证；
- macOS Developer ID 签名、notarization 和 stapling；
- 发布主体、官网、仓库、下载域名和 updater endpoint 一致；
- 每个产物提供版本、平台、架构和校验信息；
- README 不再把绕过系统安全机制作为标准路径。

### 8.2 凭证承诺必须按域拆开

当前实现不能支持“所有 API Key 使用系统安全存储且不进入配置备份”这一广义承诺：

| 凭证域 | 当前代码事实 | 应对外如何表述 |
|---|---|---|
| Claude profile / macOS | 使用 Keychain | 可声明该域使用系统钥匙串，但仍需实机和异常路径验证 |
| Claude profile / Windows | DPAPI 加密后以 `token_enc` 存配置 | 可声明仅当前用户可解密；备份中可能包含 DPAPI 密文 |
| WorkBuddy | Key 写入 WorkBuddy JSON；Unix 限制为 `0600` | 不能归入系统安全存储承诺；Windows 还需等价保护方案 |
| 诊断导出 | 明确排除 `token_enc` | 仍可能包含 URL、模型、路径、环境名和日志，应提供预览与数据字典 |

产品应维护凭证清单：保存位置、加密方式、备份行为、导出行为、删除行为和平台差异。设置页只呈现与实际实现一致的分域承诺。

### 8.3 TLS 与健康状态需要重新定义

普通网关模型检测通过 curl 配置启用了 `insecure`，健康检查复用该路径。因此“模型列表可返回”只能证明在跳过证书校验时接口可达，不能证明 TLS 信任链正确。公开产品应把以下状态分开：

- DNS/TCP 可达；
- TLS 严格验证成功；
- 使用用户 CA 后验证成功；
- 仅在忽略证书错误时可达；
- 鉴权成功；
- 模型列表成功；
- MCP 或模型真实握手尚未执行。

禁止用一个绿色“健康”覆盖这些不同安全含义。MCP 基础测试目前明确只做结构与 TCP 检查、不执行握手，这种诚实边界应推广到所有检测文案。

### 8.4 诊断隐私

公开产品应在导出前展示清单和样例，并让用户选择是否包含：环境名、网关域名、模型名、本机路径、同步日志和 WorkBuddy 信息。默认排除凭证和完整配置，文档说明本地用量扫描的目录、字段、保留周期，以及产品是否产生任何网络遥测。

### 8.5 高风险操作统一分级

建议建立统一风险等级：

- **低风险**：可逆、本地展示变化，可直接执行并提供撤销。
- **中风险**：跨文件或跨环境写入，必须 preview、revision 和结果摘要。
- **高风险**：删除、清空证书、绕过权限、修改系统信任，必须明确影响范围、二次确认、恢复方法和失败状态。

MCP 的交互模型应推广到“同步并修复”、证书、WorkBuddy gateway/organization 及安全设置。全局同步当前只返回摘要且可能丢失内部 warnings，不足以支撑公开产品的故障解释。

**同步删除语义 —— 触发条件已于 2026-09-12 查实并修正**

13. **已删除的 MCP 会被同步「复活」并自我固化**（`sync.rs:349-361`、`431-435`）。

    > **勘误**：两份文档此前都把触发条件写成「快照丢失」。经代码逐行核查，**快照丢失不是必要条件**——真正的触发点在 `replicas` 名单的维护口径。原描述已作废。

    **确认的代码事实（已逐行核对）**：

    - `sync.rs:349` `first_seen = !snap.replicas.contains(&r.key)`
    - `sync.rs:351-353` **Upsert 判定没有 `first_seen` 守卫**
    - `sync.rs:355-361` **Remove 判定有 `first_seen` 守卫**
    - `sync.rs:431-435` 新快照的 `replicas` 取自 `ok_replicas`，而 `ok_replicas` **只在** `:399`（内容已相等）与 `:422`（写成功）两处 push；**跳过与写失败均不 push**

    **最小触发链**：

    ```
    第 N 轮：用户删除 MCP foo → 主账户已写，同步将其从其余副本移除
             └─ 某一副本（如 ds）本轮写失败 / 被跳过
                → ds 仍留有 foo，且 ds 不在 ok_replicas 中
                → 新快照：state 无 foo、replicas 无 ds

    第 N+1 轮：ds 的 first_seen = true
             └─ ds 的 foo 与快照不等 → 触发 Upsert（:351-353 无守卫）
             └─ 其余副本不含 foo → 不产生任何变更
             └─ 结果：foo 被写回全部副本，含主账户
             └─ 新快照把 foo 记为「已达成一致」
    ```

    **严重性**：

    | 维度 | 事实 |
    |---|---|
    | 触发源 | **同步自身的正常失败路径**，非外部破坏 |
    | 可观测性 | **静默**——`:382-384` 父目录不存在的分支直接 `continue`，连 warning 都不产生 |
    | 是否自愈 | **否**。复活后写入快照，从此被视为共识状态 |
    | 固化效应 | 被跳过一次的副本**永久**不再产生 Remove |

    **优先级建议：P0**（原列 P1-7 的依据是「快照丢失属低频外部原因」，该依据已不成立）。
    「只把状态暴露给用户」的方案在此已不适用——失败本身是静默的，无法通过提示弥补。

    **修法方向（需设计确认，非定论）**：`replicas` 应按「本轮是否成功读到该副本」维护，而非「是否写成功」。
    ⚠️ **不可直接删除 `first_seen` 守卫**：该守卫用于防止新建的空副本把它没有的全部 key 判成 Remove、从而清空配置。
    改动方向会让「新副本首轮写失败」立即参与删除判定，**此副作用须先评估**。

## 十一、指标体系与验证实验

### 11.1 北极星与护栏指标

**推荐北极星：每周完成过“已验证环境启动”的活跃设备数。**

“已验证环境启动”定义为：应用生成或选择一个环境后，在目标 Shell 中启动 Claude CLI，启动前后的 wrapper/sync 流程完成，且产品收到或读取到与该环境一致的配置目录和路由验证结果；单纯点击启动、保存配置或模型列表成功均不计入。事件应使用随机本机设备标识和环境类型，不上传环境名、URL、路径、凭证或会话正文。

它要求用户不只是创建配置，而是真正完成一次产品可证明的环境启动。为避免用增长掩盖事故，应同时观察：

| 层级 | 指标 | 目的 |
|---|---|---|
| 激活 | 安装到首次已验证启动的完成率与耗时 | 衡量 FTUE 是否真正通畅 |
| 核心价值 | 每周使用两个以上环境的设备占比 | 验证多环境问题是否真实存在 |
| 可靠性 | 切换验证失败率、错误成功率、回滚成功率 | 防止只看点击量 |
| 配置安全 | revision 冲突被拦截数、恢复中心使用率、未恢复失败数 | 衡量安全机制是否被用户理解并使用 |
| 留存 | 首次成功后第 4 周仍有已验证启动的设备比例 | 判断是否形成持续价值 |
| 支持成本 | 每百活跃设备的安装、Shell、TLS、凭证工单数 | 约束公开化维护成本 |
| 平台质量 | Windows/macOS 各旅程通过率与事故率 | 防止用总量掩盖单平台退化 |

任何遥测设计都必须默认最小化、透明、可关闭；若不采集远程遥测，可通过自愿诊断包、发布调查和本地聚合展示获得证据，不能暗中上传环境名、URL、路径或会话数据。

**指标执行规格：**

| 指标 | 公式与数据源 | Public Preview 初始门槛 |
|---|---|---|
| 激活率 | 7 天内至少一次已验证启动的安装数 ÷ 新安装数；本地事件或自愿匿名事件 | ≥70%，且两平台分别统计 |
| 首次价值耗时 | 首次启动应用到首次已验证环境启动的 P50/P90 | P50 ≤10 分钟，P90 ≤30 分钟 |
| 多环境使用率 | 一周内已验证启动过至少两种环境的活跃设备 ÷ 周活跃设备 | 观察指标，不作发布阻塞；连续两轮 <20% 时复核定位 |
| 错误成功率 | UI 报成功但后置验证失败的操作数 ÷ 报成功操作数 | 核心写入为 0；任何复现均阻塞扩大分发 |
| 回滚成功率 | 触发回滚且最终恢复到操作前 revision 的次数 ÷ 回滚尝试数 | 自动化 100%；实机演练 100% |
| 未恢复失败数 | 失败后无已验证回滚且无明确人工恢复步骤的核心操作数 | 0 |
| 平台旅程通过率 | 该平台版本门禁旅程通过数 ÷ 应执行旅程数 | Windows、macOS 各 100% |
| 支持负担 | 安装、Shell、TLS、凭证相关工单数 ÷ 100 台周活跃设备 | Preview 两轮后设基线；连续两轮上升则暂停扩量 |

这些数值是 Public Preview 的初始经营门槛，不替代 `CLAUDE.md` 要求的测试与发布门禁。样本不足 20 台设备时只报告原始分子/分母，不用百分比做放量决策。

### 11.2 首轮产品实验

1. **问题访谈**：访谈 8–12 位同时使用个人账户和公司网关的开发者，验证“串号/串配置/恢复”发生频率与损失。
2. **首用可用性测试**：各选 Windows/macOS 新用户完成三条 FTUE 分支，记录误解、失败点和首次成功耗时。
3. **恢复理解测试**：让用户面对外部配置冲突、损坏文件和同步 warning，观察是否能独立判断影响并恢复。
4. **WorkBuddy 重叠测试**：统计 Claude 多环境用户中实际需要 WorkBuddy 的比例；低重叠时默认模块化。
5. **成本需求测试**：只做交互原型，验证用户是否信任估算费用、愿不愿提供单价或账单数据，再决定开发。

### 11.3 阶段否决条件

出现下列任一情况，不应扩大公开分发：

- 无法在两平台稳定复现首次已验证启动；
- 安装仍要求普通用户绕过 OS 安全机制；
- 产品承诺与凭证实际存储方式不一致；
- TLS 跳过验证却显示为健康；
- 高风险写入失败后用户无法确认是否已部分生效；
- 公开 issue 中核心用户主要诉求是更多 provider，而隔离与恢复价值无人使用——此时需重新评估定位，而不是继续按假设投入。

## 十二、发布就绪门禁

### 12.0 发布通道定义

| 通道 | 受众与分发 | 产物状态 | 最低门禁 |
|---|---|---|---|
| Internal Preview | 明确受邀的开发/验证人员；不在公开 Release 或 updater stable channel 分发 | 可为本地或受限产物，必须标注非生产 | 本地门禁通过；目标旅程有回滚；已知限制书面告知 |
| Public Preview | 自愿加入的外部测试者；独立 prerelease tag、Release 和 updater channel | `prerelease: true`，不覆盖 Stable | 下述 Preview 门禁全部通过，两平台安装包均有签名与实机证据 |
| Stable | 默认公开下载和 stable updater 用户 | `prerelease: false`，正式版本 | Preview 门禁 + Stable 门禁；指标达到阈值 |

当前 workflow 只有公开正式 Release 语义，尚不能承载前两种通道。完成通道拆分前，只能进行不对外发布、不接入 stable updater 的 Internal Preview。

### 12.1 Public Preview 门禁

- 产品主体、目标用户、隐私说明和 Preview 风险清楚；
- Windows/macOS 均有签名安装包和最小实机证据；
- 内部 IP、内部组织名、私有路径和示例凭证全部清理；
- 凭证、备份、诊断和遥测数据字典公开；
- Shell 支持矩阵与实际健康检查一致；
- P0 错误成功和危险操作问题清零；
- 完整本地门禁通过，Windows/macOS CI 对目标 commit 通过；
- 有明确回滚版本、反馈入口和安全报告方式。

### 12.2 Stable 门禁

在 Preview 基础上增加：

- 两个平台连续多个版本的安装、升级和回滚实机证据；
- 关键旅程错误率和未恢复失败率达到既定阈值；
- updater 通道、签名证书轮换和旧版本兼容经过演练；
- 文档、应用、发布说明和真实行为一致；
- 安全与依赖扫描无未接受的高严重度问题；
- 支持响应、漏洞披露和数据删除流程可执行；
- WorkBuddy、Codex 同步等非核心模块各自有清楚的支持等级。

### 12.3 每次版本必须分别报告

- Windows 功能实现、自动检测、手动兜底、实机和 CI 状态；
- macOS 功能实现、自动检测、手动兜底、实机和 CI 状态；
- 未验证项、已知限制和回滚方式；
- 安装包与 updater 产物状态。

“代码已写”“单元测试通过”“CI 编译通过”“真实设备旅程通过”必须保持为四种不同陈述。

## 十三、风险清单与决策顺序

| 风险 | 类型 | 优先动作 |
|---|---|---|
| OS 无可信发行签名 | 分发/信任 | 作为公开 Preview 阻塞项解决 |
| curl `insecure` 使健康含义失真 | 安全/产品承诺 | 拆分严格 TLS 与不安全诊断状态 |
| WorkBuddy Key 明文 JSON、平台保护不等价 | 凭证/跨平台 | 分域整改或限制模块公开范围 |
| Windows 备份含 DPAPI ciphertext | 隐私/文案 | 明确备份事实、恢复边界和删除语义 |
| CA 操作错误仍可能显示成功 | 可靠性 | 修复错误传播并补双平台回归 |
| Shell 覆盖与产品承诺不一致 | 核心旅程 | 建支持矩阵、手动兜底和检测 |
| broad sync 丢 warning | 可恢复性 | 返回完整影响和操作级警告 |
| WorkBuddy 写入 revision 不一致 | 并发/数据 | 统一变更合同或降级支持等级 |
| Codex 持久化 `DefaultHasher` | 升级兼容 | 稳定 hash + registry 迁移 |
| 内部 IP 硬编码 | 公开化/隐私 | 发布前清理并增加扫描门禁 |
| 用量口径不一致 | 产品可信度 | 统一 Token 定义，账单与估算明确分开 |
| 文档与实现状态漂移 | 治理 | 文档状态、版本和 owner 制度化 |

决策顺序必须是：**先明确承诺，再校准实现；先建立信任，再扩大分发；先验证核心人群，再扩充供应商；先让失败可恢复，再增加自动化。**

## 十四、最终建议

建议将未来两个阶段定义为：

1. **可信 Preview**：围绕“个人账户 + 公司路由 + 多项目配置”的用户，把安装、Shell、TLS、凭证、诊断、恢复和双平台证据做完整；WorkBuddy 作为可选集成。
2. **可靠控制面**：把 MCP 已验证的变更安全模型推广到所有高风险配置，形成环境证明卡和恢复中心，再依据用户证据选择费用、能力矩阵或第二同步目标。

不建议以“功能数量追平 CC-Switch”为阶段目标。更合理的竞争方式，是让用户在一次真实事故中明显感受到：这个产品知道变更了什么、为什么失败、有没有串线，以及如何退回去。
