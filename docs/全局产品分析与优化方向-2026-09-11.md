## 一、产品定位

产品对外名为「Claude 管理中心」。从实际形态看，**核心是一个「多环境隔离与可靠变更」工具**：

一台机器上并存多套 Claude Code 身份（网关地址 + 凭证 + opus / sonnet / haiku 三档模型映射），通过终端入口切换上下文，并在会话间共享 Skills / Plugins / Agents / Commands / MCP。

本机真实配置（A 级，实际读取 `~/.cc-manager/config.json`）：

| 实例 | 类型 | 三档模型映射（opus / sonnet / haiku） |
|---|---|---|
| `hq` | router | glm-5.3 / qwen3.8-max / deepseek-v4-flash |
| `ba` | router | claude-fable-5 / claude-opus-4.8 / claude-sonnet-5 |
| `ds` | router | deepseek-v4-pro / deepseek-v4-flash / deepseek-v4-flash |
| `jdw` | router | gpt-5.6-sol / gpt-5.6-luna / gpt-5.6-terra |

**四个实例全部指向第三方网关，三档模型横跨 glm / deepseek / gpt / claude 四个模型家族。**

### 1.1 对外公开后的定位建议

> **短定位**：Claude Code 多环境隔离与可靠变更中心
>
> **价值主张**：在个人账户、公司网关和多个项目配置之间安全切换；每次变更看得见，发生故障退得回去。

**不建议**把「用 Claude Code 的壳跑其他模型」作为对外定位。它只描述了一种现象，无法覆盖官方账户、配置隔离与恢复价值，并会把产品拖入纯 provider 数量竞争。

### 1.2 明确不做

- 不追求最多 provider preset
- 不扩张为所有 AI 工具的统一超级客户端
- 不建设第三方插件 / Skill 市场
- 不在有价格来源与账单对账前宣称「真实成本」
- 不在缺少证据时宣称「企业级安全」「所有凭证均进入系统安全存储」「零数据外发」「Windows/macOS 完全等价」

## 二、证据分级与验证边界

本文采用四级证据标注：

| 等级 | 含义 | 可用于什么结论 |
|---|---|---|
| **A｜实机证据** | 在真实 Tauri 桌面应用中完成并记录 | 仅限记录覆盖的平台与旅程 |
| **B｜自动化证据** | 有测试或工作流覆盖 | 证明被测逻辑，不等于真实设备体验 |
| **C｜代码事实** | 静态实现可确认 | 说明当前行为设计，不保证环境中必然成功 |
| **D｜产品假设** | 需求、市场或价值推断 | 必须通过访谈、遥测或实验验证 |

**本轮验证边界**：Windows 有真实 WebView2 实机记录（`docs/桌面端实机验证-2026-09-08.md`）；macOS 仅有代码分支与 CI 矩阵配置，**无本轮可引用的真实设备端到端记录**。CI 文件存在不等于当前提交本轮已运行通过。本轮无代码改动，未重跑开发门禁。

## 三、三大核心闭环

### 闭环 1：切换（产品心脏）

切换动作的实现本身可靠：生成集成脚本 → 写 shell 配置 → 建目录链接 → 共享扩展。

问题在**用户如何够到它**：

| Shell 环境 | 集成状态 | 证据等级 |
|---|---|---|
| PowerShell 5.1 | 集成行位于 `Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1` | **A**（本机实测）|
| PowerShell 7（`pwsh`）| ❌ 不生效，且健康检查**误报「已接入」** | C |
| cmd.exe | ❌ 未覆盖 | C |
| **Git Bash / MSYS** | ❌ 未覆盖（本机实测无集成行） | **A** |
| macOS zsh / bash | 代码同时写 `.zshrc` 与 `.bashrc` | **C**（代码存在，实机未验证）|

**关键事实（C 级，架构性）**：

终端入口是一个 **shell 函数**，只在已加载集成的 shell 中存在。在未加载的 shell 中，`claude` 就是上游 CLI 本身，**产品对其没有任何控制权**。

因此第 1 版设想的「任何 shell 下敲未知实例名都给提示」**无法靠现有架构实现**。要达成该目标，必须另建 **PATH 级 launcher / shim**，这是一个独立且明显更重的工程项。

**失效的后果（C 级，推断）**：在未覆盖的 shell 中执行 `claude hq`，`hq` 会按 `claude [prompt]` 的用法被当作**提示词**发给当前生效的账户——未切换、产生真实调用、污染会话历史，且零提示。

**产品侧当前唯一能做的**：应用内展示各 Shell 的检测结果与支持矩阵，**并明确不给出「可直接复制 `claude <环境名>`」的成功暗示**（因为产品无法知道用户下一个终端是哪个）。

### 闭环 2：同步

跨实例共享采用基于快照的三方合并；Codex 同步为单向。存在三个数据安全弱点：

1. **已删除的 MCP 会被「复活」并自我固化** —— *触发条件已于 2026-09-12 查实修正*

   > **勘误**：本条此前（含第 1 版）把触发条件写成「快照丢失」。经代码逐行核查，**快照丢失不是必要条件**，原描述作废。

   真正的触发点在 `replicas` 名单的维护口径（`sync.rs`）：

   - `:431-435` 新快照的 `replicas` 取自 `ok_replicas`，而它**只在** `:399`（内容已相等）与 `:422`（写成功）两处 push——**跳过与写失败均不 push**
   - `:349` `first_seen = !snap.replicas.contains(&r.key)`
   - `:351-353` **Upsert 判定没有 `first_seen` 守卫**
   - `:355-361` **Remove 判定有 `first_seen` 守卫**

   因此：**任何一轮被跳过的副本会从下一轮快照的 `replicas` 里消失 → 其 `first_seen` 变 true → 从此对它永不产生 Remove，但它残留的 key 照样 Upsert 回 target。**

   最小触发链：用户删除 MCP → 某一副本本轮写失败 / 被跳过（仍留着该 key，且被踢出 `replicas`）→ 下一轮该副本的残留 key 被 Upsert 写回**全部副本含主账户** → 新快照把它记为共识状态，**此后不再自动清除**。

   严重性：触发源是**同步自身的正常失败路径**而非外部破坏；失败**静默**（`:382-384` 父目录不存在的分支连 warning 都不产生）；后果**不自愈**；被跳过一次的副本**永久**不再产生 Remove。

   修法方向（需设计确认）：`replicas` 应按「本轮是否成功读到该副本」维护，而非「是否写成功」。⚠️ 不可直接删除 `first_seen` 守卫——它用于防止新建空副本把全部 key 判成 Remove 而清空配置。
2. **持久化哈希跨版本不稳定**：`codex_sync.rs:59-60` 的 `last_source_hash` / `last_target_hash` 用 `std::collections::hash_map::DefaultHasher` 计算并**持久化**，参与跨版本的自动同步决策。Rust 官方不保证该 hasher 跨版本稳定 → App 随工具链重编译后可能整体失配，把「两边都没改」误判为冲突，**静默停掉自动同步**（失败方向保守，不误删）。
3. **锁的陈旧判定偏弱**：`sync.lock` 仅按 mtime 60 秒判定（`sync.rs:452-482`），写了 PID 但从不读回。

> **分级说明**（修正第 1 版）：`mcp/storage.rs:175-196` 的 `revision` 用于进程内短生命周期的冲突检测，跨版本不稳定的实际影响有限，**不列为高危**。本项高危仅指 Codex 的**持久化**哈希。

### 闭环 3：诊断

`model_pin_warnings` + 一键还原命中了真实痛点（网关上没有配置里写的模型，而 Claude Code 报的错难以理解），诊断报告导出也做得扎实。

**已覆盖**（修正第 1 版）：健康检查**会**并发探测 router 的模型接口（`health.rs:277-290` 起线程调 `detect_models_blocking`），因此「网关可达性 + 模型列表」**已被覆盖**。

**仍空白**：延迟、额度、模型可用性历史（昨天有的模型今天是否还在）、请求失败归因（429 / 401 / 模型不存在）。

**新发现的严重问题（P0）**：模型检测走 curl 且配置中带 `insecure`（`main.rs:1386`），健康检查复用该路径。因此：

> **「模型列表可返回」只证明「跳过证书校验时接口可达」，不构成 TLS 信任链正确的证明。**

健康状态必须拆分，禁止用一个绿色「健康」覆盖不同安全含义：

| 状态 | 含义 |
|---|---|
| DNS / TCP 可达 | 网络通 |
| TLS 严格验证成功 | 证书链可信 |
| 使用用户 CA 后验证成功 | 自签网关正常 |
| 仅在忽略证书错误时可达 | **当前检测实际覆盖的范围** |
| 鉴权成功 | 凭证有效 |
| 模型列表成功 | 接口格式正确 |
| MCP / 模型真实握手 | 尚未执行 |

**另有一处「错误成功」**：导入 / 清空 CA 证书后重建集成脚本失败被吞掉——

```rust
// main.rs:1331 与 1347
let _ = install_integration(&list);
```

紧接着无条件返回「证书已导入（累计 N 张）」。脚本重建失败时 `NODE_EXTRA_CA_CERTS` 永远进不了 `cc.ps1` / `cc.sh`——**用户看到成功，终端依然连不上网关**。

## 五、价值缺口

### 5.1 缺口 A：统计了 token，但用户想管的是钱和额度

用量页有 7 张卡片、趋势图、模型占比，做工很好。但用户在用**多个第三方网关**，这些网关几乎必然有额度 / 计费概念，而产品**完全没有价格维度**——「真实消耗」卡片自己的说明都写着这是「模型实际处理量」，不是计费量。

对多网关用户，真正的问题是：

> 我这个月在哪家花了多少、还剩多少、下次该切到哪家？

当前用量页回答不了任何一个。

> **前置条件（采纳对照文档）**：在有价格来源和账单对账之前，**不得宣称「真实成本」**。本项应先做需求验证（用户是否愿填单价、能否接入账单 API），再决定开发。

### 5.2 缺口 B：网关能力差异不可见

**本轮实测（B 级，扫描本机全部 `.jsonl` 会话文件，未按 `message.id` 去重）**：

| 实例 | 主要模型 | assistant 记录数 | 其中 `cache_creation > 0` | 累计 cacheCreate |
|---|---|---|---|---|
| 主账户 | claude-opus-5 / 4-8 / fable-5 | 12,219 | 12,206 | 161.2M |
| `ba` | claude-sonnet-5 / opus-4-8 / fable-5 | 525 | 525 | 3.69M |
| `hq` | glm-5.3 为主 | 24,597 | 145 | 2.34M（全在 qwen3.8-max）|
| `ds` | deepseek-v4-pro / flash | 3,338 | **0** | **0** |
| `jdw` | gpt-5.6-* | 553 | **0** | **0**（且 `cacheRead` 也为 0）|

同一份约 54K 的上下文：

- 在 `ds` 上：首轮 `input_tokens: 53918`，次轮 `cache_read_input_tokens: 54144` → **缓存生效**
- 在 `jdw` 上：**完全没有缓存**，每轮全量重算

**结论（修正第 1 版）**：只能得出「**各网关的遥测行为差异显著，值得做同任务对照验证**」。

第 1 版由此推导「成本可能相差一个数量级」**已撤回**——价格未知、样本未去重、无同任务对照。同一个错误正是本文档批评产品的地方（把「处理量」当「计费量」），不应重犯。

**但证据等级需要提级**：对照文档把「网关能力矩阵」列为 P1 Discovery（先验证再开发），理由是 `/v1/models` 不足以证明缓存。该理由成立，**但它未考虑本地会话记录这一更强的证据源**——上表即为直接证据。因此：

> 能力矩阵**不是从零开始的假设**，其输入已有一半在手：缓存行为差异已由本地实测证明。**需要验证的是费用维度**，不是缓存维度。

### 5.3 缺口 C：没有「撤销」

底层实现相当讲究（事务化写入 `mcp/storage.rs:517`、备份轮换 5 份、`delete-staging`、删除空间全量回滚 `main.rs:1078-1164`），但**全部停留在实现层**，用户能按的只有「备份配置」一个按钮。

### 5.4 缺口 D：首次体验

默认落在「空间管理」（`App.tsx:141`），空态只提示「点新建」。

**修正第 1 版**：CA 证书**不是**通用首用步骤——它只适用于自签公司网关分支。首次使用应按意图分三条分支（采纳对照文档）：

- **分支 A｜官方 / 独立账户**：验证 CLI → 创建账户空间 → 安装终端入口 → 启动验证
- **分支 B｜公共可信第三方网关**：创建路由空间 → 验证 URL / 凭证 / 模型列表 → 映射三档 → 启动验证
- **分支 C｜自签公司网关**：先完成分支 B；**仅当 TLS 失败且组织提供 CA 时**才进入证书引导

> **分支 C 的前置依赖（P0）**：产品必须先能区分「证书链失败」与「DNS / TCP / 鉴权 / 业务错误」。当前检测固定使用 `insecure`（`main.rs:1386`），**无法触发分支 C**。

首次成功标准不是「保存了一条配置」，而是用户完成一次**可证明的启动**并理解当前身份、路由与配置边界。

### 5.5 缺口 E：术语未收敛

| 出处 | 用词 |
|---|---|
| CLAUDE.md / README | 实例 |
| 侧栏导航 | 空间 |
| 页面标题 | 空间管理 |
| GuidePanel | 实例配置 |

### 5.6 缺口 F：危险操作防护等级不均衡

| 功能 | 防护等级 |
|---|---|
| MCP 所有写操作 | 工业级：preview → confirm → 脱敏 diff（`McpPanel.tsx:664-754`）|
| 删除空间 | 严谨：不可恢复告知 + 全量回滚 |
| WorkBuddy 删除组织 | 有二次确认（`WorkBuddyPanel.tsx:381-398`）|
| **清空 CA 证书** | **点下即执行，不可撤销**，仅底部一行小字（`CaCertButton.tsx:141-155`）|

建议建立统一风险等级：**低**（可逆、本地展示，可直接执行并提供撤销）/ **中**（跨文件或跨环境写入，必须 preview + revision + 结果摘要）/ **高**（删除、清空证书、绕过权限、修改系统信任，必须明确影响范围 + 二次确认 + 恢复方法 + 失败状态）。

## 九、做对了的地方

1. **MCP 子系统的写入安全**：preview → confirm → 脱敏 diff → revision 校验 → 锁内复检 → 事务 + 中断恢复 + 备份轮换 + 多重回滚。`mcp/storage.rs` 有 65 个测试覆盖，含「未知字段保留」「损坏文件不覆盖」「伪造 original 拒绝」「同长度内容变更」。
2. **模型钉死告警 + 一键还原**（`health.rs:91-97`）：命中极难排查的真实痛点。
3. **前后端脱敏规则对齐**（修正：`mcpForm.ts:74-97` 与 `validation.rs:20-45` 是**两份独立实现**，非共享代码，存在漂移风险——应改为共享规则源或加一致性测试）。
4. **MCP 校验不执行任何命令**：全程只做文件存在性检查，无 `Command::new`（`validation.rs:391-419`），无命令注入面。
5. **密钥不进日志**：全目录仅 3 处 `log_line`，只记 error / warning 文本。
6. **前端竞态防护**：`inFlight` ref + 请求代号，且有测试覆盖旧请求丢弃。
7. **无权限提升设计**：用 `certutil -user` + Junction 规避 sudo / UAC，方向正确。
8. **无 `panic!` / `todo!` / `unreachable!`**：生产路径仅一处 `expect`（Tauri 启动）。
9. **`delete_profile` 的删除事务**（`main.rs:1078-1164`）：快照 → stage rename → 逐步删除 → 核验残留 → 全量回滚，是全项目最严的写路径。
10. **扩展市场克制**：明确不承担第三方扩展市场与安装责任，避免过早引入供应链负担。

## 十二、一句话总结

**这个产品的核心（多身份隔离与可靠变更）已有扎实的底层机制，但它把三件事当成了实现细节而非产品能力：切换失败时的可见性、跨网关的能力差异、以及配置的可撤销性。既然已决定对外公开，最优先的就不再是把这三件事做完，而是先把「用户凭什么信任这个安装包」这条链路建立起来——否则功能越多，被引向一条未经验证的分发链路的用户就越多。**
