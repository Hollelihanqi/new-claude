### CA 迁移不是"一次就完"—— 标记已改为**指纹集合**（2026-09-12 修正）

用户指出：**保留的 CA 迁移标记不能成为永久跳过检查的理由**。成立，且是**真缺陷**：
原实现写的是布尔标记（"做过一次"），于是用户在**旧版**里再导入一张证书（旧版只会往
`ca-cert.pem` 追加）之后，新版会**永远漏掉它** —— 对应网关联不上自签网关，
而报错现场是 TLS，离原因很远。

改法：标记内容改为**已迁移证书的 SHA-256 指纹集合**，每次启动做**增量补齐**；
旧格式（`1`）视为"当前 ca-cert.pem 里的都算已迁移"，之后的增量仍会被识别。
反过来也不会碍事：用户已按网关删掉的证书不在"新证书"里，不会被塞回去。
判定抽成纯函数 `certs_pending_migration` 并有专门回归测试。

### P0-A#3 修正 TLS 语义与健康状态 —— 已完成（代码改完，未提交）

**根因**：`main.rs` 的 `detect_models_blocking` 在 curl 配置里硬编码 `insecure`（= `-k`）。三个调用方共用：`detect_models`、`detect_models_for_blocking`、`health.rs` 的网关项。后果两条：
1. **安全**：`Authorization: Bearer <API Key>` 被送到证书未验证的连接上，on-path 中间人可截获。
2. **语义**：健康项把"跳过校验时可达"渲染成 `ok` /「可达，Key 有效」，而 claude(Node) 始终校验证书（全仓库无 `NODE_TLS_REJECT_UNAUTHORIZED`），所以是假阳性。

**修法**：`insecure` 全部移除，改为严格分级探测 —— ①严格+系统信任；②仅当①以证书类退出码失败**且** `ca-cert.pem` 存在时，回退到 `--cacert` 已导入 bundle。失败按 curl 退出码分为 证书/网络/鉴权/响应 四类，各自给可执行文案。

**实测证据（Windows，两个 curl 二进制均为 Schannel）**：

| 实测项 | 结果 |
|---|---|
| `--cacert <无关 CA>` 访问公有 CA 站点 | **rc=60** ⇒ `--cacert` 是**替换**信任库，不是追加 |
| Windows 路径原样写进 curl 配置 | `\t` 被解释成**制表符**，路径被静默破坏 ⇒ 必须正斜杠化 |
| 正斜杠路径 `C:/Users/.../ca.pem` | 被正确加载（rc=60） |
| 自签网关 + `--cacert` 指向其 CA | **仍 rc=60「revocation status is unknown」** |
| 加 `ssl-revoke-best-effort` | **200 + 模型列表** |
| 完整梯子（本地自签 HTTPS 网关） | 第 1 步 rc=60 → 第 2 步 200，端到端走通 |

**两条容易踩的坑（都已写进代码注释与回归测试）**：
- `--cacert` 替换语义 ⇒ **不能无条件传**，否则打挂所有公有 CA 网关；只能作回退。
- Schannel 强制查 CRL/OCSP，自签 CA 没有 CRL 分发点 ⇒ 即使链验证通过也 rc=60。而 claude(OpenSSL) 不查吊销，故加 `ssl-revoke-best-effort`（仅"吊销信息拿不到"时放行，真被吊销仍失败）。该标志 **Schannel 专有**，不能按操作系统硬编码 —— 已改为运行时解析 `curl --version` 判断后端（`TlsBackend`），并缓存。

**独立安全复审抓到两个真缺陷（已修）**：

1. **失败被报成成功**：`interpret_probe` 原先只特判 401/403，其余状态码直接解析 body。curl 不带 `--fail` 时 HTTP 错误也是退出码 0 ⇒ 一个 **502 错误页只要 body 恰好长得像模型列表就会被报成「健康」** —— 正是本次要根除的假阳性。修法：抽出纯函数 `probe_verdict(exit_code, http_code)`，**只有 2xx 才算成功**，状态码取不到（标记缺失 ⇒ 0）同样算失败。表驱动测试钉死。
2. **API Key 泄进诊断报告**：`BadResponse` 把网关控制的响应体（≤160 字）原样拼进用户可见文案，而健康详情会写进**导出给别人看的**诊断报告。网关/前置代理在错误页里回显 `Authorization` 头并不罕见 ⇒ Key 泄漏。修法：新增 `redact_secret`，并明确 **`interpret_probe` 是构造用户可见文案与抹 Key 的唯一出口**（原先放在 `run_curl_probe`，多一条构造路径就会漏 —— 这条是测试先抓出来的）。

**复审确认无问题的部分**：不存在"证书未验证却发 Key"的路径；`build_curl_config` 任何分支都不含 `insecure`；`parse_http_code` 用 `rsplit_once` 取最后一段，**响应体伪造状态码不可行**（curl 的 write-out 永远在最后）；无 `unwrap`/索引 panic 风险。

**顺带修正（同批）**：
- `Tls` 类文案原先对所有 TLS 退出码都劝"导入 CA"，但 58/59/64/66/80/82/90/91/98 导入 CA 帮不上忙（如 98 = 要求客户端证书）。新增 `is_ca_import_likely_helpful`，只有信任链类（51/60/77/83）才断言"导入 CA"。

### P0-A#6 修复 CA 操作后的静默失败 —— 已完成

**根因**：`import_cert` 与 `clear_certs` 用 `let _ =` 吞掉 `install_integration` 的返回值。证书文件写成功了，但集成脚本刷新失败时**照样报成功** —— 而集成脚本正是导出 `NODE_EXTRA_CA_CERTS` 的地方，刷新失败 = 证书完全不生效，用户却以为「已导入，重开终端就好」，实际连不上网关。

**修法**：
- 两处 `let _ =` 改为 `if let Err(e) = … { return Err(…) }`。**不回滚已写入的证书**（留着用户修好集成后即可生效），但错误文案要如实说清：证书已写入、终端集成刷新失败、当前不生效、怎么修。
- `clear_certs` 侧危害较小（`generate_sh/ps1` 有 `if [ -f … ]` 兜底），但仍如实报出。

**顺带修掉同类的第二处**（P0 条目没点名，但同源）：`install_integration` 的 **macOS 分支** `let _ = ensure_line(.zshrc)` / `let _ = ensure_line(.bashrc)` 同样吞错 —— 两个 shell 配置都没写进去时，终端根本不会 source 集成脚本，却返回 Ok。修法用新抽的纯函数 `fold_shell_config_results`：全成功 / 部分失败（用户可能只用一种 shell，可接受）/ **全部失败才报错**。

**回归护栏（已做变异测试验证）**：
- 纯函数 `fold_shell_config_results` 的三态断言（可在任一平台覆盖 macOS 分支）
- `integration_refresh_errors_are_never_swallowed_again`：扫源码禁止吞错写法复现。needle 在**运行时拼接** —— 否则测试文件自己的注释就会命中自己（第一版就是因此假失败）。
- **变异测试**：把吞错写回源码，护栏立刻失败并给出正确原因（`FAILED` + "install_integration 的错误又被吞掉了"）；恢复后 198 全绿。**即护栏确有判别力，不是空跑。**

### P0-B#12 Codex 持久化哈希跨版本不稳定 —— 已完成

**根因**：`stable_hash` 用 `std::collections::hash_map::DefaultHasher`，而 Rust **明确不保证它跨版本/跨编译稳定**。该值被**持久化**进 registry，参与"源/目标有没有被改过"判定 ⇒ 重编译后全部对不上 ⇒ 每条都读成 `(true,true)` = **Conflict** ⇒ 自动同步**静默停摆**（失败方向保守、不误删，但用户看不出原因）。

**修法**：
- `content_hash` 改用 **sha2**（已有依赖），格式 `sha256:<hex>`，**带算法前缀**便于将来换算法时识别旧值
- `is_legacy_hash` 识别旧值；`sync_status` 对旧值返回 **`NotSynced`**（历史未知 ⇒ 按首次同步处理，会给出"继续会覆盖同名 MCP…保留目标端专属设置"的警告，那正是此刻的真实情况）。**不新增状态、不改前端**。
- `target_hash`（备份文件名用）一并改为稳定算法

> **改 `target_hash` 时我引入了一个 Windows 非法文件名**：`sha256:` 里的 `:` 在 Windows 文件名中非法 ⇒ `fs::rename` 报 `os error 87`。**被既有测试当场抓到**（5 条测试挂）。修法是文件名用途去掉前缀。

**测试**：`legacy_hashes_rebaseline_instead_of_reporting_conflict` —— 旧值 → `NotSynced`；新格式照常比较（否则就是"修了迁移、废了功能"）；一边旧一边新也算旧。

**门禁**：`pnpm build` / `pnpm test`(**59**) / `cargo test`(**218**) / `cargo fmt -- --check` / `git diff --check` 全绿。

### F1 profile 事务锁 —— 已完成

**问题**：`save_profile` / `delete_profile` 的「读 → 改 → 写」全程**没有持有配置锁**。与正在运行的 `claude --sync` 并发时，`save(&list)` 会用**加载时的陈旧 list** 覆盖对方的改动（丢更新）；`delete_profile` 的失败回滚同理会在别人的写入之上做恢复。

**修法**：
- `sync::forget_profile` 拆成**非重入内部函数** `forget_profile_locked`（不加锁），并删掉已无人使用的加锁包装 —— 锁不可重入，而"彻底删除"是要在同一把锁内完成多步的复合事务（写配置 → 刷新集成 → 忘记快照 → 清理残留 → 失败回滚），中途某一步自己去抢锁会直接失败。这正是审查建议的 `forget_profile_locked` 形态。
- `save_profile` / `delete_profile` 在函数**入口**取锁；`delete_profile` 的**回滚路径也在锁内**。
- 先核实了无重入风险：`save_profile` 只作为 Tauri 命令注册（无内部调用方），`forget_profile` 只被 `delete_profile` 调用；main.rs 另外三处取锁（`read/write_instance_settings`、`set_bypass_permissions`）都不在调用链上。

**测试**：结构化护栏 `profile_mutations_hold_the_config_lock`（扫源码断言两个函数入口都持锁 + 删除路径用 `_locked`）。**已做变异验证**：去掉 `save_profile` 的取锁后，护栏立刻失败并报「fn save_profile 没有在入口处持锁」。

> 护栏第一版**自己 panic**：`&source[start..start+900]` 按**字节**切，而源码含中文 ⇒ 切在字符中间。已改为按字符切。这是本项目第二次在"用 `include_str!` 扫自身源码"的护栏上踩到自引用/切片问题。

### 审查 #10：CA 逐网关隔离 —— 已实现（**macOS 未验证**）

**权威依据**：[`CA逐网关隔离设计-2026-09-12.md`](./CA逐网关隔离设计-2026-09-12.md)（含触及面、机制、撤销范围规则、迁移、验收标准、实现记录）

**问题**（审查成立）：`cert_path()` 只有一个 `~/.cc-manager/ca-cert.pem`，`import_cert` 追加进这一个文件，
而**每个 router 都注入它** ⇒ 给网关 A 导入的私有 CA 同时成为网关 B 的信任根。与约束 5 冲突。

**改法**：`~/.cc-manager/ca/<环境名>.pem`，每个网关一份，**互不共用**；
生成脚本、curl 探测回退都只读**该网关自己的**那份。
**不搞"共享 bundle ∪ 网关 bundle"** —— 任何全局共享的 CA 按定义就是所有网关都信任，等于把缺陷换个名字留下。

**三个容易做错的地方（都已写进注释与测试）**：

1. **清空时撤销范围必须重算**：从 A 删掉的证书可能仍被 B 需要。无条件撤销会让 B 连不上，
   而文件还在 B 那里、用户完全看不出原因。规则见 `certs_to_revoke`，有专门测试。
2. **PEM 判等要归一化，写回必须用原文**：最初的实现把空白全去掉再返回，

### 审查 #12：发布「晋级」不再重建旧 Tag 的产物 —— 已实现（**待真跑 Actions 验证**）

**问题**（审查成立，已核实）：`test` / `build` 两个 job 都是裸 `actions/checkout@v4`（**无 `ref`**），
而 `workflow_dispatch` 允许对**已存在的 draft Tag** 走"晋级" —— 于是测试与构建的是**当时的分支**，
产物却经 `tagName` 挂到那个旧 Tag 上。同一个 Tag 的代码与安装包可变，发布不可变性被破坏。

**改法**（`.github/workflows/release.yml`）：

1. `channel` job 新增输出 **`mode`**：`promote`（Tag 已存在且仍是 draft）/ `build`（新 Tag）。
2. `test` / `build` 加 `if: needs.channel.outputs.mode == 'build'` —— **晋级时一个都不跑**。
   理由写进了注释：那个 Tag 的测试在它自己那次构建里已经跑过，再跑一遍测的是"当时的分支"，
   只会给人"这个 Tag 通过测试"的错觉。
3. 两个 job 的 checkout 固定到该 Tag：`ref: ${{ github.event_name == 'push' && github.ref || github.sha }}`
   （推送时是 Tag 本身；手动建新 Tag 时是触发提交 —— `tauri-action` 会把 Tag 建在那个提交上）。
4. `publish` 新增**产物核验**（fail-closed）：必须有 macOS `.dmg`、Windows `.msi`/`.exe`、`latest.json`，
   缺任一项就**拒绝公开**，并提示"晋级只复用已有产物，确实要重建请换新 Tag"。
5. `publish` 的 `if` 改为 `needs.channel.result == 'success' && (needs.build.result == 'success' || skipped)` ——
   因为 promote 路径上 `build` 是 skipped，默认的"依赖被跳过就跳过"会把晋级也一起跳过。

**本机已验证**：YAML 结构（4 个 job、`mode` 输出、两处 checkout 固定）、
产物核验的 shell 逻辑（完整产物通过；缺 mac / 缺 latest.json / 空产物**全部拒绝**）。

**未验证（必须真跑一次 Actions）**：`if` 与 `needs` 的跳过语义、`ref` 表达式的实际取值、
以及上面那份清单新增的 8.5a / 8.5b 两条。**在此之前不得宣称发布流程已修复。**

### P0-A#4 已知的入手点（本次排查中新增两条证据）

做 A#3 时查到**两处 CA 信任链不一致**，都是 CLAUDE.md 禁止的「两平台能力不等」，建议并入 A#4：

### P0-B#13 已查实的根因（尚未修）

`sync.rs:431-435` 新快照的 `replicas` 取自 `ok_replicas`，而它**只在** `:399`（内容已相等）与 `:422`（写成功）两处 push —— **跳过与写失败均不 push**。于是被跳过的副本从下轮快照 `replicas` 名单消失 → `first_seen` 变 true → `:355-361` 的 Remove 判定被跳过（但其残留 key 仍会经 `:351-353` 的**无守卫 Upsert** 复活）→ 写回全部副本并固化进快照。

**注意**：两份文档此前把触发条件写成「快照丢失」是错的，**已作废**。

#### 修法方向也已作废（2026-09-12 推导，附反例）

上文曾写「`replicas` 应按『本轮是否成功读到该副本』维护」。**逐条推演后确认这个方向会造成镜像的、且更严重的缺陷，不得照做。**

两种维护口径的失败面：

| `replicas` 按…维护 | 副本写失败时的表现 |
|---|---|
| **写成功**（现状 `ok_replicas`） | 副本从名单消失 → 下轮 `first_seen` → Remove 跳过，**但无守卫的 Upsert 让旧 key 复活** |
| **读成功**（上文建议） | 副本留在名单 → 下轮不缺该 key 就不再 `first_seen` → 被读成"用户在此处删除" → **该 key 从所有副本被删除** |

**关键**：这两种情形在数据上**完全同形** —— 文件可读、内容缺 key。无法从现有快照信息区分"它是因为我们写失败才缺"还是"用户真的删了"。

**因此不能改用读成功口径**：复活是可再删一次的烦人；而删除传播会让一份有效配置在所有副本上消失。**拿一个更坏的缺陷换现在的缺陷，不做。**

#### 正确修法需要记录「每个副本的上次确认状态」

要区分上述两情形，快照必须保存**逐副本的已确认内容**（或其哈希），而不只是一个名字列表。那时的判定才成立：
- 副本当前内容 == 上次确认值 → 未被外部改动
- 副本缺某 key 且它上次确认时**有**该 key → 真删除
- 副本缺某 key 且它**没有**已确认基线（从未写成功过）→ 不可判定，保守跳过

这是一次 `DomainSnap` 的结构改动，需配套迁移与回归测试，**不能顺手改**。

> **现状评估**：该缺陷的失败方向是"已删除的 MCP 复活"，属**非破坏性**（用户可再删）。在正确修法落地前，保持现状是更安全的选择。
