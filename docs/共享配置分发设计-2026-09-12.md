## 一、要解决的问题

现状（已核实的偏差 2）：

- `sync_configs_locked`（`sync.rs:686-700`）把 `~/.claude.json` 与 `~/.claude/settings.json` 当成
  **可写副本**，与各环境做**双向合并** ⇒ 应用会改写用户直接敲 `claude` 时用的那份配置。
- 而且这**不只是"多写了一个文件"**：MCP 的「用户级」作用域（`user:__main__`）**正是**靠这条链
  把配置分发给各环境的（`mcp/mod.rs:408-419`、`mcp/storage.rs:519`）。
  直接删掉那两行会让它**静默失效**（写入成功、环境里没有、无报错）。

**目标**：共享配置改由**应用自建共享源**持有，**单向分发**到受管理环境；默认 Claude 完全退出这条链。

## 二、数据模型

### 2.1 共享源（应用独占管理）

| 文件 | 内容 | 对应域 |
|---|---|---|
| `~/.cc-manager/shared/mcp.json` | `{"mcpServers": {…}}` | MCP |
| `~/.cc-manager/shared/plugins.json` | `{"enabledPlugins": {…}}` | 插件启用状态 |

两个域各占一个文件，与现状一致（`mcpServers` 在 `.claude.json`、`enabledPlugins` 在 `settings.json`）。
**分发机制复用，合并规则不照搬** —— 见 §三。

### 2.2 分发台账（关键）

`~/.cc-manager/shared/distribution.json`：

```jsonc
{
  "version": 1,
  "domains": {
    "mcpServers": {
      "envs": {
        "corp": {
          // 本应用**上次分发给该环境**的条目值（按条目名）
          "corp-server-a": { "cmd": "npx", "args": ["-y", "x"] },
          "corp-server-b": { … }
        }
      }
    },
    "enabledPlugins": {
      "envs": {
        "corp": { "some-plugin@market": true, "other@market": false }
      }
    }
  }
}
```

**为什么必须有它**：判定"环境里这条是它自己的配置，还是我们发下去的"，**不能只看"目标里已经有这个名称"**。
只有记住"上次发下去的是什么"，才能把下面三件事区分开：

| 情形 | 数据上长什么样 | 必须怎么判 |
|---|---|---|
| 我们发过、用户没动 | 环境值 **==** 台账值 | 可继续跟随共享源更新 |
| 我们发过、用户改过 | 环境值 **!=** 台账值 | **环境覆盖**，分发不得覆盖它 |
| 从来没发过（环境自己的配置） | **台账无记录** | **环境独立配置**，不得当成"我们发过的" |

> 这正是 P0-B#13 那一类缺陷：缺少"上次确认状态"就无法区分「我们没写成功」与「用户真的改了」。

## 三、分发算法（单向）

对每个域、每个受管理环境，逐条目名 `name`：

| 共享源 | 环境文件 | 台账 | 判定与动作 |
|---|---|---|---|
| 有 | 有，值相同 | — | **一致**。不报冲突，但保留"来自共享"的来源标识 |
| 有 | 有，值不同 | 有且 == 环境值 | 我们发的、用户没动 → **更新为新的共享值**，更新台账 |
| 有 | 有，值不同 | 有且 != 环境值 | **环境覆盖** → 保留环境值，报「已覆盖共享配置」，可查看差异 |
| 有 | 有，值不同 | 无记录 | **环境独立配置**（重名）→ 保留环境值，报「已覆盖共享配置」 |
| 有 | 无 | 有记录 | 我们发过、环境侧后来没了 → **视为环境覆盖（用户删了它）**，不复活，报冲突 |
| 有 | 无 | 无记录 | **新增**：写入环境，记台账 |
| 无 | 有 | 有记录 | 共享项被删除 → **清掉环境侧这条继承值**，删台账记录 |
| 无 | 有 | 无记录 | 环境自己的配置 → **不动** |
| 无 | 无 | 有记录 | 清理台账残留记录 |

**「删除共享项：只清理继承该项的状态，保留环境自己的覆盖设置」** = 上表第 7/9 行：
只有台账里有记录的（= 我们发过的）才清；环境的覆盖不动。

**幂等**：第二遍跑时，每条的台账值都等于环境值 ⇒ 全部落到"一致"或"覆盖"，零写入。
（验收要求"重复分发结果稳定"。）

**只动应用管理的条目**：写入时只增删改上表涉及的那些 key，
环境的 `settings.json` / `.claude.json` 其余字段（登录态、permissions、用户自己的插件…）原样保留。

## 四、首次迁移

1. **只读采集**：把现有 `~/.claude.json` 的 `mcpServers` 与 `~/.claude/settings.json` 的 `enabledPlugins`
   写入应用共享源 —— **仅当共享源文件不存在时**（幂等，只在首次做）。
2. 之后**不再读**默认 Claude。它既不是持续共享源，也不接受写回。
3. **各环境现有值一律保留**：不统一、不静默覆盖。它们要么与共享项同名（→ 判为"环境独立配置/覆盖"），
   要么只存在于环境（→ 不动）。
4. 记迁移版本号，避免重复执行。

> 「不**持续**作为共享源」正是本节的措辞依据：默认 Claude 可以当**一次性种子**，之后退出。

## 六、验收标准（用户指定，逐条可测）

**MCP**
1. 环境独立配置与共享项**同名、内容不同** → 保留环境配置，显示「已覆盖共享配置」，可查看两边差异。
2. 同名、内容**相同** → 不报冲突，但保留来源标识。
3. 此前由应用分发的条目 → **不得误判为环境独立配置**；共享源更新时正常更新。
4. 用户修改过已分发的条目 → 识别为环境覆盖，后续分发**不得覆盖**它。
5. 提供「恢复使用共享配置」操作，**用户明确执行后**才撤销覆盖。

**插件**
6. **默认 Claude 的文件未被改写**。
7. **单个环境显式 `false` 不被覆盖** —— 显式 `false` 必须保留，不能当作"未设置"。
8. **重复分发结果稳定**（幂等）。

**共同**
9. 分发只动应用管理的条目，保留 `settings.json` 其余字段。
10. 删除共享项时只清理继承状态，保留环境自己的覆盖。

### 后端接线做了什么（2026-09-12）

- **单一解析点**：`storage::user_source_path(paths, inst)` —— `__main__` → `~/.cc-manager/shared/mcp.json`，
  其余环境 → 各自的 `.claude.json`。`source_file` / `current_file` / `read_service_config` / `collect_state`
  四处共用。**必须只有一个解析点**：写入与读取用了不同解析，症状就是"保存成功、界面里却没有"
  （这次接线时真的踩到了 —— `collect_state` 一开始没跟着改）。
- **`local_parts` 拒绝 `__main__`**：项目本地作用域曾经可以选"默认 Claude"，写的是
  `~/.claude.json` 的 `projects[...]`，与只读约束冲突。现在后端硬拒绝（不依赖界面过滤）。
- **`sync_configs_locked` 改为分发**：GUI 的「同步并修复」、`--sync`、`apply_mcp_change`
  三处入口自动切到单向分发，且**先 `ensure_seeded()`** 再分发。
- **删除环境时清理台账**（`forget_env`）：不清的话，将来重建同名环境时那条"我们分发过 X"
  会让 X 被判成"用户改过/删过"，再也收敛不到共享值。残留核验也从快照改为台账
  （`ledger_references_env`）。
- **环境覆盖会报出来**：分布结果里的 overrides 全部进 warnings —— 静默保留会让用户
  以为共享值已经生效。

### 已实现的引擎（`shared_config.rs`）

- `decide(shared, env, ledger)` —— §三 表格的**全部规则**，是唯一的判定出口。
- `plan_env` / `apply_plan` —— 单环境单域的计划与改写；`apply_plan` **只动计划点名的条目**，
  其余字段（登录态、permissions、用户自己的条目）原样保留。
- `distribute_to(field, shared, ledger, targets)` —— **可测内核**（显式路径，
  照本项目已有的 `*_at` 惯例），`distribute(field)` 是收集真实路径的薄壳。
- 台账**按"当前认为分发过什么"重建**，不是打补丁：共享项已删且两边都没了的残留记录会自然消失。

**两个由测试抓出来的自身缺陷（值得记住）**：

1. **解析失败被当成"文件不存在"** —— 原先写 `read_to_string().ok().and_then(parse).unwrap_or(默认空对象)`，
   于是环境那份 `.claude.json` 只要**暂时不可解析**（正被写、被改坏），本轮就会把它**整个换掉**，
   连登录态和项目记录一起丢。现在分开处理：不存在 → 从空对象开始；存在但读不了/解析失败 → **跳过并告警**。
   （与 `sync.rs` 既有的"解析失败的副本不应被覆盖"同一条原则。）
2. **台账在"共享项已删且环境侧也没了"时留残留** —— 会让用户将来重新加同名条目时被误判成
   "我们发过的"。改成按当前认知重建后自然清掉。

**未覆盖的验证**：`distribute()` 收集真实路径那段（`crate::load()` / `env_path`）没有单测 ——
它依赖真实 `home()`/`cfg_dir()`。核心逻辑已在 `distribute_to` 上测全；
另有一条结构不变量测试钉住"分发目标永远在 `~/.claude-split/<环境>/` 下、绝不可能是默认 Claude 的文件"。
