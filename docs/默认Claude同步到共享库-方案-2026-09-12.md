## 一、要解决的问题

决策 7.3 让**默认 Claude（`~/.claude/`）与受管理环境的共享库（`~/.cc-manager/shared/`）在迁移后正式独立**。
这在安全边界上是对的（应用对默认 Claude 只读），但带来一个日常割裂：

> 用户在默认 Claude 里装了新技能 → **环境里看不到**；而扩展中心那句
> 「扩展仍通过 Claude Code 或本地文件管理」在迁移后**已不属实**。

本方案给这件事一个**明确、可预期、不需要用户做决定**的答案。

## 三、D2 是本方案里最反直觉的一条，先给证据

**决定：`plugins` 不做文件复制。** 依据是**本机实证**，不是推断：

```jsonc
// ~/.claude/plugins/installed_plugins.json（本机实测，节选）
{
  "version": 2,
  "plugins": {
    "ecc@ecc": [{
      "scope": "user",
      "installPath": "C:\\Users\\hq\\.claude-split\\hq\\.claude\\plugins\\cache\\ecc\\ecc\\2.0.0",
      "version": "2.0.0",
      "installedAt": "2026-07-13T08:55:22.683Z",
      "gitCommitSha": "40927950c49f6e742d341e20ff7b9b7e1e7bfff5"
    }]
  }
}
```

**这条数据说明三件事**：

1. `installPath` 是**绝对路径**，且是**安装那一刻解析出来的**；
2. 它甚至**已经绑到了具体环境**（上面指向 `.claude-split\hq\...`——因为该环境的 `plugins`
   是链接，Claude Code 写入时解析到了环境侧）；
3. 账本还带 `version` / `gitCommitSha` / `installedAt` —— 它是**安装状态的账本**，不是文件清单。

⇒ 把这份 JSON 复制进共享库，所有环境都会读到"这份插件的文件在 **hq** 的目录里"。
**结果不是"插件可用"，而是"账本与文件对不上"** —— 用户看到"插件在列表里但不可用"，
比没有更难排查。（决策 7.3 里那句「不能自动判断的插件目录 → 停止切换链接」防的正是这个。）

**正确做法：让 Claude Code 自己完成安装**（账本由它自己写，两边一致、可更新、可卸载）。
本机实测 `claude plugin` 子命令族存在：

```
install|i <plugin>     Install a plugin from available marketplaces
                       (use plugin@marketplace for specific marketplace)
list                   List installed plugins
enable / disable       …        details / eval / marketplace / init
```

界面能做的是：**只读列出默认 Claude 装了什么**，让用户选择插件和目标环境；
随后应用为每个目标环境分别设置 `CLAUDE_CONFIG_DIR`，并直接调用 Claude Code 官方
`plugin install / enable / disable / uninstall` 命令。展示列表优先只读解析插件账本，避免仅为展示
而启动 Claude CLI；安装和变更状态时才调用官方 CLI。

> **一句话**：`skills/agents` 是**文件资源**；`plugins` 是**每个环境各自持有的安装状态**，
> 共享的是管理策略，实际安装必须由 Claude Code 在各环境分别完成。

### 3.1 已确认的插件管理模型（2026-09-13）

插件拆成三层：

| 层 | 内容 | 归属 |
|---|---|---|
| 插件来源 | `plugin@marketplace`；不钉死版本 | 应用共享插件策略 |
| 环境策略 | 继承 / 启用 / 停用 / 排除 | 应用管理 |
| 实际安装 | 插件文件、缓存、`installed_plugins.json` | 各环境，由 Claude Code 官方 CLI 管理 |

硬边界：

1. 各环境的 `.claude/plugins` 必须独立，不能继续链接到同一个共享目录；
2. 共享库不得保存或复制 `installPath`、插件缓存及 `installed_plugins.json`；
3. 「所有环境」表示为每个环境分别执行官方安装，不表示多个环境共用插件目录；
4. 默认 Claude 只作为插件清单的只读来源，应用不得在默认 Claude 中安装、启停或卸载插件；
5. 调用插件命令只注入目标环境的 `CLAUDE_CONFIG_DIR`，不得携带网关地址、模型 Key 或 CA 配置；
6. 批量安装按环境独立报告成功与失败，成功环境不因其他环境失败而回滚；
7. 同一插件已存在时：保留并展示环境实际版本；PathMux 不自动拉齐版本，只有用户主动点击「更新」才调用官方 CLI 更新目标环境；
8. 「停用」表示保留安装文件但不启用；「排除」表示该环境不继承共享安装策略，两者不得混同。
9. 插件安装、启用或停用成功后，新启动的 Claude Code 会话直接生效；该环境中已经运行的会话
   需要在各自会话内执行 `/reload-plugins`，不需要关闭终端窗口；包含 monitors 的插件例外，
   需要重启 Claude Code 会话。
10. 应用不得强制中断或向正在工作的 Claude Code 会话注入命令。完成操作后显示「已安装；
    已打开的 Claude 会话请执行 `/reload-plugins`」；批量安装时对每个目标环境显示该状态。
11. `plugin update` 按 Claude Code 官方命令说明提示“重启会话后应用新版本”，不能用
    `/reload-plugins` 的通用提示覆盖更新场景。

### 3.2 存量共享插件目录必须先迁移

旧版本曾把 `plugins` 放在 `SHARED_SUBDIRS` 中，并把各环境的插件目录链接到共享根。
当前版本已实现可回滚迁移：逐环境盘点 → 暂存旧链接 → 建立独立目录 →
用官方 CLI 重新安装并核验 → 成功后解除旧链接；任一环境失败，只恢复该环境旧链接并标记「待迁移」。
旧共享插件目录在所有环境迁移完成前不得删除。

## 四、D4：冲突不提示，靠规则消灭

用户明确要求：**不要让用户看到冲突提示**（会不知所措）。比"少提示"更好的是**让冲突不存在**：

> **同步只补缺，不覆盖。**

| 默认 Claude | 共享库 | 行为 |
|---|---|---|
| 有 | **没有** | ✅ **拉过来** |
| 有 | **也有**（内容相同或不同都一样） | ⏭️ **一律不动** |

于是自动同步**没有任何需要用户决定的分支** ⇒ **没有冲突提示**。

**那"我在默认 Claude 改了一个已有技能"怎么办？** 用 **D5 手动单条同步**兜：
用户明确点某一项时，界面给他两句选择（默认那句是安全的）：

- 「只同步共享库里没有的」（默认）
- 「**用默认 Claude 的版本替换共享库里的同名项**」← 明确写出后果，由他主动点

**为什么不做成"静默跳过且不记录"**：那样用户问"我在默认 Claude 改了，环境里为什么没变"
就无从解释。所以保留 **D7 的被动记录**（要主动点开才看到，不需要他做任何事）。

## 五、各范围的最终形态

### 5.1 skills / agents

| 能力 | 形态 |
|---|---|
| 一键全量 | 扩展中心顶部「从默认 Claude 同步」 |
| 单条同步 | 每个条目一个同步按钮（D5 的两选项） |
| 自动 | 见 §六 |

Skill 的管理粒度是**一个完整的顶层 Skill**，不能复用 `copy_tree_merge` 对已存在目录逐文件补齐。
否则可能把默认 Claude 与共享库中的两个不同版本拼成一个混合版本。新增和替换都必须先复制到
临时目录、校验，再以整个 Skill 为单位切换；任何失败保持旧版本。

#### Skill 管理方式（2026-09-13：产品行为已确认，技术方案已收敛）

1. 共享 Skill 保存在 `~/.cc-manager/shared/skills/<skill-name>/`；
2. 环境不再链接整个 `skills` 目录，改为按每个 Skill 单独建立链接；
3. 每个环境对每个 Skill 有四种状态：继承共享 / 环境覆盖 / 环境排除 / 环境独有；
4. **共享 Skill 新增或更新成功后，默认立即在所有环境生效**（用户已确认）；
5. 被明确设为「环境排除」的环境不建立该 Skill 的链接；
6. 环境存在同名本地 Skill 时，保留环境版本并标为「环境覆盖」，不得静默覆盖（用户已确认）；
7. 同名覆盖不弹冲突决策；用户主动执行「恢复继承」后，才移除环境覆盖并重新使用共享版本（用户已确认）；
8. 从默认 Claude 导入的符号链接 Skill，应解析来源并复制独立快照到共享库，不把外部链接继续传播给所有环境；
9. 从共享库删除一个默认 Claude 仍然存在的 Skill 时，记录忽略项，防止后台自动导入再次把它恢复；
10. 默认 Claude 中同名但内容不同的 Skill，自动导入只记录跳过，不弹出冲突决策；用户主动选择「更新共享版本」时才整体替换。

Skill 页签的管理范围：

| 范围 | 操作含义 |
|---|---|
| 所有环境（共享库） | 新增或更新共享 Skill，成功后立即提供给所有未排除、未覆盖的环境 |
| 指定环境 | 设置排除 / 恢复继承，或安装该环境独有的 Skill |

旧版整目录链接会在首次分发时先复制为真实目录，再按 Skill 逐项写入独立快照；每项采用临时目录、
内容校验、备份与原子替换。这样 Windows 与 macOS 使用同一套覆盖判定，也不依赖链接监听。

#### Codex/ChatGPT 桌面工具支持（需求与接入方案已定，待真机验证）

共享 Skill 的默认目标包含：

- 所有 PathMux 管理的 Claude Code 环境；
- 当前 OpenAI Codex/ChatGPT 桌面工具、Codex CLI 与 IDE 扩展共用的个人 Skill 目录。

默认 Claude 不属于写入目标，仍只作为只读发现来源。

本机现状显示 Codex 同时能发现 `~/.codex/skills` 与 `~/.agents/skills`，而默认 Claude 的大量
Skill 又链接到 `~/.agents/skills`。因此不得把任一根目录整体改成 PathMux 链接，避免覆盖系统 Skill、
循环链接以及间接改写默认 Claude。建议适配规则：

1. PathMux 继续以 `~/.cc-manager/shared/skills/<name>/` 作为唯一共享源；
2. Claude 环境通过各自 `.claude/skills/<name>` 接入；
3. Codex 当前版本通过 `~/.codex/skills/<name>` 按 Skill 接入，绝不触碰 `.system`；
4. `~/.agents/skills` 与 `~/.codex/skills` 都纳入只读盘点。同名已有内容视为 Codex 本地版本，
   不覆盖；内容一致则视为已满足共享策略；
5. Skill 使用 Agent Skills 的公共结构。对 Claude 专属或 Codex 专属扩展字段做兼容性标记，
   不自动改写用户的 `SKILL.md`；
6. Codex 接入后必须验证新 Skill 能在下一轮对话出现；若链接监听不稳定，改为原子复制分发，
   不能要求用户重启桌面应用来掩盖实现问题。

这里不再要求用户选择技术路径：优先采用本机现状已经使用的逐 Skill 接入方式；平台或版本验证发现
链接监听不可靠时，由实现自动降级为原子复制 + 分发记录。两种方式必须保持相同的产品行为：默认可用、
同名本地版本优先、删除共享版本不伤害本地版本。

#### 运行中会话的生效规则与验证边界

Claude Code 官方变更记录说明：从 2.1.0 起，`~/.claude/skills` 和项目 `.claude/skills`
中新建或修改的独立 Skill 支持自动热加载，正常文件路径下不需要 `/reload-plugins` 或重启会话。
`/reload-plugins` 是插件变更入口，不应作为独立 Skill 的常规提示。

PathMux 最终采用逐 Skill 原子复制，不再把 Junction / 符号链接传播到目标。运行中会话能否在两个平台
稳定收到新增、更新与删除事件仍需真机验证。因此产品承诺分两步：

1. 代码设计上，在共享 Skill 新增、更新、删除后原子替换每个受影响环境的 Skill 目录项，主动制造可观察的文件系统变更；
2. Windows 与 macOS 真机分别验证「会话先启动，再新增 / 更新 / 删除 / 排除 Skill」；验证通过后界面写
   「已对运行中的 Claude Code 自动生效」，未验证或检测失败时提示重新启动 Claude Code 会话。

### 5.2 Commands 退役与存量兼容（2026-09-13 用户确认）

新版 Claude Code 已把旧式 `.claude/commands/*.md` 合并进 Skills 使用模型，现有文件继续兼容，
但新工作流应使用 `.claude/skills/<name>/SKILL.md`。PathMux 因此：

1. 不再提供独立 Commands 页签；
2. 不再自动导入默认 Claude 的 Commands；
3. 不提供新建、安装或共享 Command 的入口；
4. 升级时不得删除用户已有 `.claude/commands` 内容；
5. 后续提供一次性「转换为 Skill」迁移：转换成功并验证后再退出旧 Commands 链接；同名 Skill
   已存在时不覆盖，原 Command 保留在迁移备份中等待人工处理。

扩展中心已经移除 Commands 页签、导入与新增入口；新版启动流程也不再执行包含 `commands` 的旧整目录
迁移。`SHARED_SUBDIRS` 只保留给删除安全与旧迁移回归测试，已有 `.claude/commands` 数据不会被删除。

### 5.3 plugins

| 能力 | 形态 |
|---|---|
| 展示 | 默认 Claude、共享策略和各环境真实安装状态分开展示 |
| 从默认 Claude 安装 | 只读取插件身份；用户选择目标环境后，由应用在各环境分别调用官方安装 |
| 新装插件 | 输入 `plugin@marketplace`，安装到所有环境或指定环境 |
| 启停 | 支持继承 / 启用 / 停用 / 排除；环境可以覆盖共享策略 |
| 更新 / 卸载 | 对目标环境逐个调用官方 CLI，并逐环境显示结果 |

插件页位于现有「扩展中心 → Plugins」页签。页签顶部提供目标范围、
「安装默认 Claude 的插件」和「安装插件」；这些控件不出现在 Skills / Agents 页签。

### 5.4 MCP

| 能力 | 形态 |
|---|---|
| 展示 | 「默认 Claude 的 `mcpServers`」列表（只读 `~/.claude.json`） |
| 导入 | **手动**：单条或全部「导入到共享库」 |
| 之后 | 走**既有的单向分发**（`shared_config` → 各环境），不新增机制 |

### 5.5 Agents（2026-09-13 用户确认）

Agents 是 Claude Code 的自定义子代理定义，默认共享到所有 Claude 环境。实现规则：

1. 共享源为 `~/.cc-manager/shared/agents/<name>.md`；
2. Agent 是单个 Markdown 文件。Windows 对文件符号链接有权限限制，因此优先采用原子复制 + 分发台账，
   不依赖整个目录或单文件链接；
3. 新增共享 Agent 后立即分发到所有环境；
4. 环境文件仍等于上次分发值时，跟随共享更新；环境自行修改后标为「环境覆盖」，后续不得覆盖；
5. 环境可以排除共享 Agent，也可以拥有环境独有 Agent；
6. 删除共享 Agent 时只删除仍处于继承状态的环境副本，覆盖版和环境独有版保留；
7. 保存前校验 frontmatter、名称、工具限制、模型字段，以及 `skills:` 引用在目标环境是否可用；
8. Agents 只分发给 Claude Code 环境。Codex 的多任务 Agent/线程不是同一种配置文件，不做错误转换；
9. 运行中 Claude Code 对 Agent 文件变更是否即时发现必须真机验证，未验证前不承诺热加载。

以上分发方式、环境覆盖 / 排除 / 环境独有、原子复制台账和依赖缺失处理均已由用户确认。

## 六、自动同步：形态比功能重要

**不做系统定时任务**（Windows 计划任务 / macOS launchd）—— 那属于系统级侵入，
安装/卸载容易残留，与本项目「不残留」的要求冲突。

**采用：应用启动时机会式检查**

1. 启动时读「上次同步时间」；
2. 距上次 **> 3.5 天**（即一周两次的等效节奏）才跑一次；
3. 跑完更新时间戳。

三条硬规矩：

- **只拉不推**：只读默认 Claude、只写共享库。**约束 4（对默认 Claude 只读）不被破坏**；
- **只补缺**（D4）：永远不覆盖共享库里已有的东西；
- **可关 + 有记录**：设置里能关；记录「上次同步：时间 / 新增 N 项 / 跳过 M 项」。

- **冲突不弹窗**（D4）；「跳过 2 项」是一行静态文字，**点开才展开明细**（D7）；
- 插件操作必须明确写「安装到环境」，不得写成复制或同步插件文件。

### 7.1 功能说明按钮（2026-09-13 用户确认）

在用户需要理解“影响谁、背后会发生什么”的功能旁放小型圆形 `?` 按钮。按钮规范：

1. 鼠标悬停或键盘聚焦显示一句短提示，例如「了解共享 Skill 如何应用到各环境」；
2. 点击后从右侧打开统一的「它是怎么工作的」说明面板，不使用会打断操作的多层弹窗；
3. 面板分为两层，但都属于正文：顶部是简短的**使用说明**，下面是默认展开的**设计原理**，不能把设计原理藏在多层折叠内容里；
4. 使用说明回答：**它能做什么 / 操作后会发生什么 / 会影响哪些地方 / 你还需要做什么**；
5. 设计原理回答：**数据从哪里来、写到哪里、如何判断共享与覆盖、失败时怎样保护原数据、运行中的会话如何发现变化、对应的主要代码模块在哪里**；
6. 对数据流或判断流程优先使用小型流程图、路径示例或伪代码，避免粘贴大段源代码；关键实现文件可以列出，但不写容易失效的固定行号；
7. 可以使用“单向分发、分发记录、原子写入”等准确术语，但第一次出现必须紧跟一句白话解释。例如：“原子写入：先写入临时文件，成功后一次替换，避免只写了一半”；
8. 每个面板必须给一个真实例子，并说明至少一个异常场景，例如同名覆盖、权限不足、目标环境正在使用或依赖缺失；
9. 技术细节必须与当前版本的真实实现一致。尚未实现或尚未真机验证的行为要明确标成“计划支持”或“待验证”，不得写成现有能力；
10. `?` 按钮必须有可读的无障碍名称，支持键盘打开、Esc 关闭并把焦点送回原按钮；
11. 说明正文随对应页面懒加载，公共包只保留很小的按钮和面板外壳，不能增加首页初始体积。

首批必须覆盖的位置与用户文案：

| 位置 | 说明重点 |
|---|---|
| Skills 页标题 | 共享 Skill 保存后，所有 Claude 环境和 Codex 默认都能使用；某环境自己的同名版本优先 |
| 「自动导入新增项」 | 应用打开时定期检查默认 Claude，只带回新项目，不修改默认 Claude，也不覆盖共享库已有项目 |
| 「环境覆盖 / 排除」 | 覆盖表示该环境使用自己的版本；排除表示该环境暂时不用共享版本 |
| Plugins 页标题 | 插件会在每个环境分别由 Claude Code 安装，不共用安装目录 |
| 插件安装结果 | 安装/启停/卸载后，已打开的会话执行 `/reload-plugins`；更新与 monitors 需要重启 Claude Code 会话 |
| Agents 页标题 | Agent 像一位有明确职责的专业助手，会在单独的工作区思考后把结果交回来 |
| Agent「缺少依赖」 | 该 Agent 需要某个 Skill 或 MCP；应用只告诉用户缺什么，不会擅自安装或打开 |
| MCP 一级页标题 | MCP 是 Claude 连接外部服务的工具入口，本身不会思考或主动执行任务 |
| MCP「所有环境 / 指定环境 / 当前项目」 | 用例子解释配置会出现在哪里，以及其他环境是否能使用 |
| Codex 支持 | 同一个共享 Skill 会分别提供给 Claude 环境和 Codex；默认 Claude 仍然只读 |

示例——Agents 页的说明正文：

> **它能做什么**：Agent 像一位专门负责某类工作的助手，例如代码审核员或测试员。
> **点击后会发生什么**：共享 Agent 会提供给所有 Claude 环境。Claude 可以把合适的任务交给它，
> 它完成后把结果交回当前对话。
> **会影响哪些地方**：只影响 Claude 环境，不会自动变成 Codex Agent。
> **你还需要做什么**：如果显示“缺少依赖”，按提示补充对应 Skill 或 MCP；应用不会擅自处理。

其后直接展示“设计原理”，例如：

> **数据怎样流动**：共享 Agent 保存在应用自己的共享目录。保存成功后，应用把完整文件分别写入各个
> Claude 环境，并记录本次写入内容的特征。以后更新时，只有仍与上次分发版本一致的环境副本才会跟随更新。
>
> **为什么不会覆盖环境修改**：如果环境里的文件已经和上次分发内容不同，应用会把它识别为“环境覆盖”，
> 保留该环境自己的版本。这里使用“分发记录”，意思是应用记住自己上一次写了什么，而不是仅凭文件名猜测来源。
>
> **失败时如何保护数据**：新内容先写入同目录的临时文件，确认完整后再替换正式文件。任何一个环境写入失败时，
> 界面列出失败环境；不能把部分成功说成全部成功。
>
> **实现位置**：列出负责共享存储、分发判断、环境覆盖识别和界面状态展示的主要模块，方便开发者继续查看源代码。

## 九、验收标准

1. 自动同步**从不覆盖**共享库里已有的条目（构造同名不同内容，跑两轮，共享库内容不变）。
2. 自动同步**从不向默认 Claude 写入任何字节**（比对 `~/.claude` 全树哈希，前后一致）。
3. **任何情况下不向用户弹出需要决策的冲突提示**。
4. 一键同步把默认 Claude 独有的 `skills/agents` 带过来；同名项被跳过，Commands 不参与。
5. 手动单条同步在用户显式选择"替换"时，**只替换那一条**，其余不动。
6. 共享 Skill 新增或更新后，所有未排除、未覆盖的环境立即使用新共享版本；环境排除和环境覆盖保持不变。
7. 删除共享 Skill 后，所有继承链接被清理；环境独有和环境覆盖版本保持不变，并且自动导入不会复活已忽略项。
8. 在 Claude Code 会话已经运行的前提下新增、更新、删除和排除独立 Skill，Windows 与 macOS 均能热加载；
   不依赖 `/reload-plugins`。若逐 Skill 链接方案无法稳定触发，必须改用能触发监听的分发方式，不能只改提示文案。
9. plugins 面板按默认 Claude / 共享策略 / 环境真实状态分层展示，应用不直接写
   `installed_plugins.json`；所有插件改变通过目标环境的 Claude Code 官方 CLI 完成，成功后只核对状态并记录策略，
   不再由 PathMux 补写环境 `enabledPlugins`。
10. 各环境的插件目录彼此独立；删除任一环境不会让其他环境的插件 `installPath` 失效。
11. 批量安装部分失败时准确列出成功与失败环境，并可只重试失败项。
12. 安装、启用或停用成功后准确提示运行中会话执行 `/reload-plugins`；新会话无需额外操作，
    monitors 类型明确提示重启 Claude Code 会话。
13. MCP 导入后，各环境**按既有分发机制**拿到该条目（含「环境可覆盖」语义）。
14. 关掉自动同步后，启动不再触发拉取。
15. 约定间隔内只跑一次（连开三次应用，只同步一次）。
